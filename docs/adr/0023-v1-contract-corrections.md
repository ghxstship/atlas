# ADR 0023: Corrections to the Frozen v1 Contract

- Status: Proposed (amends ADR 0014)
- Date: 2026-10-15
- Decider: Orchestrator

## Context

ADR 0014 froze the OpenAPI v1 document at Wave 1 exit (1,307 operations), when most of the schema did not exist yet. The frozen request and response shapes were written from the spec, not from tables. Wave 3 module agents now find that their tables cannot fill those shapes faithfully:

- `created_by` and `updated_by` are required UUIDs in every tenant read shape, but the columns are NULL for seed, platform and system rows.
- Create bodies omit NOT NULL columns that have no default (`ProjectCreate` has no `project_key` or `time_zone`).
- Fields the contract requires are nullable columns, fields the contract names do not exist, and some resources have a different shape altogether (positions as a count instead of rows, validity in months instead of days, `role_type` instead of `pool_kind`).

Agents leave those operations without handlers, so the API cannot reach parity with the UI (Section 19.6). Changing a frozen operation is a breaking change, and Section 18 gate 20 forbids breaking changes within `/v1`. But v1 has never been released: `API_VERSION` is `1.0.0-draft.1`, no SDK has shipped and no third party depends on it.

## Decision

1. **Corrections while v1 is a draft.** While `API_VERSION` is a `1.0.0-draft.N` prerelease, a frozen operation or component may be corrected to match the implemented schema. Once 1.0.0 is released, the rule of ADR 0014 and Section 10.1 applies without exception: changes within `/v1` are additive only, and a breaking change needs `/v2`.
2. **Every correction is an entry.** A correction exists only as an entry in the machine-readable list: contract-wide entries in `packages/api/src/catalog/corrections.ts`, module entries in the module's own file `packages/api/src/catalog/modules/<module>.ts` (next to its additive operations, so parallel branches never edit a shared list, ADR 0021). Each entry carries an id, the draft it entered (`since`), the module, the resources and components it changes, what changes, why (naming the table, view or migration), and the edit itself. `CORRECTIONS`, exported from `@xos/api`, is the resolved list in the order applied.
3. **Edits are declarative.** `packages/api/src/catalog/correct.ts` provides the edits: field nullability, removal, rename, addition with its create and update placement, server-set and immutable fields, verb and action removal, actions with capabilities, and the default order (including a descending feed order). Edits never mutate the frozen definitions in `@xos/schemas`, which stay as frozen.
4. **Gate 20 enforces the list.** `packages/api/test/corrections.test.ts` keeps a digest of every operation and component of the frozen document (`packages/api/src/catalog/frozen-v1.digest.json`, cut once from commit 5d269b9 and never regenerated while v1 is a draft). It fails when:
   - the uncorrected frozen catalog no longer generates the frozen document, so any edit to a frozen source outside a correction fails;
   - the corrected document changes, adds or removes a frozen operation or component that no entry lists;
   - an entry changes nothing it lists;
   - an entry is dated later than the current draft, or any entry exists once `API_VERSION` is a release.
5. **Each draft that adds corrections bumps `API_VERSION`.** This ADR's corrections ship as `1.0.0-draft.2`. The info version tells SDK generators and reviewers that the draft changed shape.
6. **Proposing a correction.** A module agent adds an entry to its own module file in its own branch, with a reason, regenerates the document and the operation types, updates its handler contract tests where the shape changed, and lists the entry in its completion report. The orchestrator reviews every entry at merge (packages/api/README.md, "Correcting the frozen contract").
7. **At release.** Releasing 1.0.0 re-cuts the digest from the released document and empties the correction list; the entries stay recorded in this ADR's register. From then on gate 20 compares against the released document and accepts no corrections.

## Audit of the frozen catalog against the schema

Every catalog resource was compared with its table or view on the shared stack `xos4-shared`, reset to `main` with all 117 migrations and the demo data, on 2026-10-15. The comparison is repeatable: `pnpm --filter @xos/api audit:contract --sql` prints one read-only query over `information_schema` and `pg_catalog`, and `audit:contract --dump <file>` audits its result (`--uncorrected` audits the catalog as frozen; without it, the corrected catalog). It checks:

- **Nullability:** a field the contract requires as non-null whose column is nullable. View columns always report nullable, so views are not checked for it.
- **Names and types:** contract fields with no column, columns the contract omits, and JSON types a column cannot carry.
- **Enums:** contract enum lists against the Postgres enum labels, and Title Case patterns that reject a label.
- **Create bodies:** NOT NULL columns without a default that the create body omits (path parameters and the base columns excepted), fields the body requires whose column is nullable or has a default, and optional fields whose column is NOT NULL without a default.
- **Money:** minor-unit columns stored as anything but integers, and rows with minor-unit columns but no currency column.

### Scope of the corrections

- **Every resource** gets the contract-wide audit-field correction: `created_by` and `updated_by` become nullable.
- **Built modules** get the corrections their resources need: Projects, Home and Activity (A07); Opportunities and People offers (A28b); Identity and Settings (A30); Gateway (A28, A27); Platform (A18); Show plus `records.archive` and `recordReplans` of Work (A08); and the Canon resources that map to a canon table (A01).
- **Operations that already have handlers** keep their shapes apart from relaxations (nullability) and table names, so their handlers and contract tests stay valid. The one exception is the project read shape, which gains `time_zone`, `venue_id`, `client_counterparty_id`, `production_state` and `archived_at`; the A07 handler selects them.
- **Modules not built at the time of the audit** (Schedule and Work beyond the A08 items, Knowledge, Places, Logistics, Advancing, Hospitality, Assets, People other than offers, Crew, Credentials, Finance, Procurement, Vendors, Safety and Reports) get only the audit-field correction. A13 merged People and Crew after the audit, and their migrations 0462, 0463 and 0981 were not yet on the shared stack. The remaining findings are listed below for each module agent, who proposes corrections through decision 6.
- **Canon deferred to the canon owner:** the Playbook library mirrors (`canonStdDocumentLibrary`, `canonStdEnumerations`, `canonStdRadioChannels`, `canonStdSops`, `canonStdVendorClasses`, `canonStdVendorEntitlements`, `canonStdVerbiage`), `canonStdRoles` (xpms.role is a sheet mirror; the Roles Library decision D12 is open), `canonStdLaborRateCards` (no canon table, only sheet views), `canonProductionTemplates`, `canonSupersessions` (keyed by domain and code, not one code), `canonRatifications` (the table has no id), `canonIntake` and `canonExtensions` (xpms.intake is the canon pipeline's discrepancy table, not tenant proposals) and `canonUrns` (resolution is a function, not a table). Their shapes depend on the open owner decisions of ADR 0014 (items 1, 5 and 7), so this ADR leaves them as frozen.
- **A field with no column is not always wrong:** a handler may derive it. The activity feed reads `app.activity_feed`; A07, A08 and A28b map renamed columns such as `transitioned_at` from `created_at`, `node_kind` from `scope_kind` and `answer` from `answer_text`; bid totals come from their lines and representation scopes, webhook events, custom object values and profile-share fields from child tables. The corrections remove a field only when no handler can fill it faithfully, and the dispositions below name the fields left to a handler or the database.

### Shared components the frozen document rendered as nullable

The generator renders a shared component (such as `PhaseCode`) from the first field that references it. When that first field wrapped the component in `.nullable()`, the frozen document emitted the component itself as nullable, which every other reference then inherited. Three corrections remove or rewrite such a first reference, so `DeptCode`, `OrgRole` and `Classification` are plain codes again, while nullable references stay nullable. The corrections list these components, and `orNull` in `correct.ts` writes a nullable component reference as `anyOf` the component and null, so a correction can never change a shared component by accident; gate 20 fails if one does.

### After the corrections

On the corrected catalog the audit finds 24 nullable columns behind required fields (all in modules not yet built or in handled operations whose handlers map them), 379 contract fields with no column (derived fields and modules not yet built), 34 resources without a source, and one enum mismatch (`approvalPolicies.document_type` lacks Requisition, noted for A15 and A18; `spendAuthorityLimits` is corrected). Run `pnpm --filter @xos/api audit:contract --dump <file>` to see the current list.

## Alternatives considered

- **Edit `@xos/schemas` directly.** It hides which frozen shapes changed and why, and gate 20 could not tell a correction from an accident.
- **Leave the operations document-only until v2.** API parity (Section 19.6) would fail for every built module, and v2 would be needed before v1 ever shipped.
- **Add new operations beside the wrong ones.** It doubles the surface with operations nobody can serve and leaves broken shapes in the published contract.

## Consequences

- Module agents can write handlers for operations their schema can now fill. The completion report of A04C lists them by module.
- The frozen digest is a second source of truth beside `openapi/v1.json`; both are generated, and neither is edited by hand.
- Corrections are visible in review as entries with reasons, not as diffs of a 4.8 MB document.
