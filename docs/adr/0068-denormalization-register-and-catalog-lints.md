# ADR 0068: Denormalization Register and Catalog Lints

- Status: Proposed
- Date: 2026-10-24
- Decider: A108 (RRR-153), for the orchestrator's review
- Addresses: trace rows S3.15-01 and S3.15-09; Section 18 gate 29
- Migrations: none

## Context

Section 3.15 says the CI schema lint fails on arrays of identifiers, relational JSON, columns that duplicate a column in a referenced table, and stored totals without a register entry. Until A108 only the first was catalog-enforced: pgTAP 1280 refused `uuid[]` columns and held a hand-written list of the other array columns. JSON columns, restated parent columns and stored totals were checked once, by hand, in the gate 29 review on d36918a, and nothing stopped a later migration from adding one. `docs/adr/denormalization-register.md` was prose that no test read, and the person-owned tables that ADR 0033 decision 69 accepts were a list inside pgTAP 0202.

## Decision

1. **The register is YAML, and the Markdown is generated from it.** `docs/adr/denormalization-register.yaml` holds the Section 3.15 register (stored derived values and materialized views, with source, refresh rule and measured reason) and six reviewed lists: own names, JSON columns, array columns, restated parent columns, stored values named like totals, and the `app` tables without the ADR 0002 tenant columns. `pnpm --filter @xos/schemas generate:denormalization` writes `docs/adr/denormalization-register.md` and the pgTAP fixture `supabase/tests/1282_denormalization_register.psql` from it; `check:denormalization` and the `@xos/schemas` unit tests fail when either is stale, in the style of `generate:shortcuts`. The loader refuses unknown fields and kinds, duplicates, unsorted lists and a `registered` entry that no derived entry names.
2. **Every list entry says why.** A JSON column carries its ADR 0002 exception: `rich-text`, `audit-diff` or `provider-payload`, or `registered` when the derived register carries the reason (form definitions). A stored total is `registered`, a `fact` (fixed when something happened, such as the rows a run delivered), or an `input` (set by a person, a provider or the canon, such as a pallet count or a pass mark). A restated column is `registered`, a `fact` (kept as it was when written while the parent can change, such as a published form version), or `own`: the row's own value, either because it can differ from the parent's (a guest's nights inside a hotel block's) or because the row needs it without the link, which is optional, and a guard keeps the two equal when the link is set (a time entry's project and its optional shift). A tenant exception is an `identity` row of Section 4.8.1, `person-owned` (ADR 0019 item 10, ADR 0033 decision 69) or `platform`.
3. **A known violation is listed with its finding.** Kind `finding` names a file under `legal/qa/findings/`. The lint then passes on the current schema while the violation stays visible in the register and the finding. Fixing the finding removes the entry, and the stale-entry check fails until it is removed. Gate 29 on batch-c 32f29903 filed A108-001 (closed lists held as text), A108-002 (stored statement totals) and A108-003 (copies through a required link).
4. **What the restated-column lint compares.** For every foreign key of an `app`, `private` or `xpms` table (partitions and self-references left out), a child column outside the key with the same name and type as a column of the referenced table, outside its primary key, is a restatement. The referenced table can be in any schema, `auth` included.
   - **Own names are never compared.** The register's `own_names` lists names that describe the row itself wherever they appear: `id`, `org_id` and the ADR 0002 row stamps, the canon's workbook provenance stamps (`source_row` and the like), the row's own words (`name`, `title`, `description`, `body`, `label`, `note`, `notes`) and its place among siblings (`ordinal`, `position`, `sort_order`). Section 3.15 names `org_id` as the convention; the rest are the same kind of name. Without them, every named child of a project, venue or org would match its parent's `name` (84 of the 354 matches on batch-c), and the list would teach reviewers to approve without reading.
   - **A foreign key made only of own names is never followed.** Every tenant table references `app.organizations` through `org_id`, and many reference `app.people` through `created_by`; following those keys would compare every column with the organization's or the author's.
   - **A composite foreign key that maps the child column onto the parent column is not a restatement,** because the database already keeps the two equal. It is the fix that lets an entry leave the register without dropping the column.
5. **What the stored-total lint matches.** A column whose name has a word `total`, `count`, `sum`, `balance`, `score`, `percent`, `percentage` or `readiness` (singular or plural, between underscores) and is not a generated column. Views are out of scope: a view computes its value.
6. **The tenant exceptions move from pgTAP 0202 into the register.** 0202 includes the fixture and refuses an `app` table without `org_id` and the five audit columns unless the register lists it, as 1280's array list moved into 1282. A new person-owned table joins the YAML with its reason instead of the SQL list. ADR 0019's amendment of 2026-10-23 points there.
7. **Every entry must still match.** The suite fails on a register entry whose column no longer exists or no longer matches its lint, so a stale entry cannot hide a new column of the same name.
8. **The lints prove themselves.** `1282_normalization_lints.test.sql` ends by creating probe tables inside a savepoint (a jsonb column, an array, a restated parent column, an own name and an `org_id` key that must not count, a stored and a generated total, then a composite foreign key) and checks that each lint reports exactly the probe, then rolls back.

## Consequences

- A migration that adds a JSON column, an array column, a restated parent column, a stored total or an `app` table without the tenant columns fails `supabase test db` until its author lists it in the YAML with a reason and reruns the generator. The diff of the YAML is the review.
- Two derived entries grew by a column the d36918a review did not name: `app.form_submissions.score` joins `max_score` (both fixed by the immutable version and answers at submission), and `app.occupancy_counters.alert_level_percent` joins `current_count` (set together under the counter's lock). Their refresh rules already covered them.
- A restatement under an own name (a child `name` that copies its parent's) is not caught by the lint; the gate 29 review reads those by hand.
- Closed lists held as text with an in-list check constraint are not linted yet. Gate 29 found 45 added since d36918a (A108-001); a lint can follow once they are converted.
- Branches that add a JSON column, a restated column, a stored total or a tenant exception after this one fail 1282 or 0202 on merge until the YAML lists them.
