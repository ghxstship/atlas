# ADR 0032: Gate 5 Handler Completion: Retired Operations and New Tables

- Status: Proposed (amends ADR 0023); Amendment 1 (A52, RRR-97) builds the retired settings features
- Date: 2026-10-19
- Decider: Orchestrator (proposed by A50, RRR-94)

## Context

Section 18 gate 5 requires a handler and a contract test for every documented operation. After Wave 6, 232 operations had no handler, mostly because their frozen v1 shape could not be filled faithfully from the schema. ADR 0023 lets a module agent correct a frozen shape while v1 is a draft. Some operations have no faithful shape at all: no table backs them, or no caller of the public API can write their table under row level security. For each of those, this ADR records whether the operation was retired through a correction or whether a table was built for it.

Corrections that only change a shape so a handler can serve it are entries in the module files under `packages/api/src/catalog/modules/` and are not repeated here.

### Policies added

Migration 1171 lets `org.time_attendance.write` rename a kiosk, move it to another project of the org and retire it (column grants on `name`, `project_id` and `deleted_at` only). Kiosks could be registered but never retired, so a lost tablet kept a working device key; `private.verify_kiosk_pin` already refuses a deleted kiosk. `kioskDevices.update` and `.delete` use it, and `kioskDevices.create` returns the device key once (correction `kiosk-device-project`).

## Consequences

- Still to build, as features rather than handlers: legal entities, the IP allow-list, access reviews, break-glass, project shares, several project roles per assignment (Section 4.8.1) and blocks. Each needs its schema, enforcement and UI, and its operations return to v1 additively once it exists. All seven are built in Amendment 1.

- The Playbook library mirrors, the Roles Library (`xpms.role`) and the canon labor rate cards (`xpms.rate_card_resolved`), which ADR 0023 left for the canon owner, are served in the shapes of their tables. Their columns are fixed by the import (Section 2.1), so the open owner decisions of ADR 0014 change their values, not their shapes.

- The retired operations leave `/v1` while it is a draft, so the published document never offers an operation that every caller is refused.
- The resource coverage list (`packages/api/src/catalog/coverage.ts`) follows the retirements.

## Amendment 1: the retired settings features are built (A52, RRR-97, 2026-10-19)

The seven features the Consequences list left to build now have their schema, enforcement and Atlas settings UI, so their operations return to v1. The corrections `settings-features-not-built`, `project-role-on-assignment` and `blocks-not-offered` are replaced by corrections that fit each frozen shape to its table (`packages/api/src/catalog/modules/parts/a52-settings.ts` and `modules/identity.ts`). Each migration has a pgTAP suite that checks the enforcement and the refusals.

The Atlas settings pages Legal Entities and Fiscal, Security (allowed networks, emergency access), Access Reviews and personal Profile Privacy (blocked people and organizations) carry the panels (`apps/atlas/components/settings/contributions/a52.tsx`). Every string is in both locales.

Open for the owner:

- **Per-role mapping for shares.** Section 8.5 says a share "maps the partner's roles onto project roles". The share holds one project role for every partner member. A mapping from each partner role to a project role is an additive table.
- **What project roles allow.** Project roles add only what `private.project_role_capabilities` lists (today, Field Supervisor dispatches incidents). That limits what a share's project role allows.
- **Direct calls to Supabase.** The IP allow-list is enforced where Atlas and the API check credentials. A client that sends a valid session JWT straight to the Supabase REST endpoint is not filtered per org. Closing that needs all browser traffic to go through the servers, or a network restriction at the Supabase project. Supabase network restrictions apply to the whole project, not per org.
- **Break-glass scope.** Break-glass grants the Owner role's capability set and passes the IP allow-list. Owners already hold nearly every capability, so its main use is reaching an org the allow-list or a custom-role change has locked out. Whether it should also lift other controls, such as an org MFA policy, is an owner decision.
