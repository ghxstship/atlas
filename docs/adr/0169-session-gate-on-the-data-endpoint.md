## Context

An organization can set three access controls: a second-factor requirement (`security.mfa_policy`), a session lifetime and idle timeout (`security.session_hours`, `security.idle_timeout_minutes`), and an IP allow-list (`app.org_ip_allowlist` with the switch `security.ip_allowlist`). Today the database only reports what an organization asks of a session (`app.my_org_auth_status`, `app.network_access`). The refusal happens in application code: Atlas on every page and server action, the XOS API before every handler, and Compass when a session starts or changes organization. The idle timeout exists only in Atlas, from a browser cookie. Gateway and Console check none of them.

Row-level security reads none of this. The policies on about a thousand tables rest on membership and capability helpers rooted in `auth.uid()`. So a call made straight to the Supabase data endpoint (PostgREST, Storage, Realtime) with a valid session token does everything the person's role allows in four cases where the apps would refuse:

1. a session without a second factor, of a member whose organization requires one (including a person who never enrolled one);
2. a session older than the organization's lifetime, for as long as its refresh token renews it;
3. a session idle longer than the organization allows;
4. a session signed out from another device, until its access token expires (up to 3,600 seconds today);

and in a fifth: a caller outside the organization's allowed networks.

Five facts shape any fix.

- **First-party clients are direct callers.** Compass reads and writes through PostgREST, Storage and one Realtime channel (PowerSync is deferred and not in production). Atlas and Gateway hand the browser the access token for a Realtime socket (`GET /auth/realtime`). Routing everything through the API is not possible on Vercel functions for websockets and 6 MB upload chunks.
- **The database cannot tell our servers from anyone else.** Atlas, Gateway, Console and the XOS API call PostgREST from Vercel as the `authenticated` role with the person's own token and no caller address. The database sees Vercel's address for all of them.
- **A pre-request check exists for PostgREST only.** Supabase documents that `pgrst.db_pre_request` does not run for Storage or Realtime; there the check has to sit in row-level security. Realtime caches broadcast and presence authorization for the life of a connection and refreshes it only on join or a new token.
- **The caller's address is not established on hosted Supabase.** `private.request_ip()` reads the forwarded chain by a hop count that was only ever observed on the local stack (finding A69-002). Storage and Realtime are not documented to give the database any request header.
- **Compass treats refusals differently by shape.** Only HTTP 401, `PGRST301` and `PGRST303` make the sync engine halt and wait for sign-in. `XR001` and `42501` turn a queued offline write into a permanent conflict, and an error-free full pull that returns nothing makes the device delete its local rows (`packages/sync/src/conflict.ts`, `apps/compass/src/data/downloader.ts`).

Three designs were drawn and two adversarial reviews judged them. Both reviews chose the same base: a gate in the database that refuses a failing direct call as a whole, before any statement runs. This record takes that base and grafts the parts of the other two that the reviews found stronger.

## Decisions

### D1. One verdict, computed in the database, from the token and the session row

`private.session_verdict()` answers two things for the current token: whether the session itself is refused, and which organizations refuse it and why. Its inputs are the standard claims `aal`, `amr` and `session_id`, the `auth.sessions` row, one row of activity per session (`private.session_state`) and one row of rules per organization (`private.org_session_rules`, kept current by triggers on `app.setting_values`, plan features and `app.org_ip_allowlist`). The custom access token hook does not change. A claim stamped at issue was rejected because it is stale for a token lifetime and makes the hook a write path on every sign-in.

The session is refused as a whole (reason `session_ended`) when a person's token has no `session_id`, no `amr` timestamp or no live `auth.sessions` row. Missing claims fail closed. This also ends the time in which a signed-out token still works.

For each organization where the caller is an active member, the session is refused when:

- `session_mfa_required`: `private.mfa_required(person, org)` and `aal` is not `aal2`;
- `session_expired`: the earliest `amr` timestamp plus the organization's `session_hours` has passed;
- `session_idle`: the longest gap between two activities of the session, or the time since the last one, exceeds the organization's `idle_timeout_minutes`. An activity is a recorded call (D5), `app.touch_my_session`, or a token refresh (`auth.sessions.refreshed_at`). The longest gap is kept, so activity after the timeout does not revive a session; only a new sign-in does;
- `network_restricted`: the organization enforces its allow-list, the caller's address (D4) is outside it, and the caller holds no open break-glass session at `aal2` (migration 1298).

An organization that set nothing gets the registry defaults, as Atlas applies them today: second factor optional, 336 hours, 60 minutes idle, allow-list off. The idle default is reviewed before `idle` is enforced (D5).

Who the verdict skips: `service_role` and requests with no token (Edge Function workers and pg_cron); `anon`; people who are not members of the organization (external collaborators reach rows through engagements, accounts, grants and shares). Tokens minted by `integration-worker`, `integration-inbound` and `automation-run` carry a signed claim `xos_origin: worker` and skip the allow-list, because they act from Supabase's own network. `api-token` is public and never sets that claim.

API keys, personal API tokens and OAuth app tokens are not sessions. They stay exempt from the lifetime and idle rules, as migrations 1330 and 1563 decided; the allow-list binds them (D4), and an OAuth app token also needs a live session row. For the second factor the owner decided one exception (owner decision 10), and the probe selects whether it is built:

- **If the probe shows that an app token's `session_id` names the session that authorized it** (`Q5.verdict` is `names-authorizing-session`): an OAuth app token is refused for an organization whose second-factor rule that session does not meet. The verdict reads the assurance level of the authorizing session from its `auth.sessions` row and gives the reason `session_mfa_required`. This is a sixth control, `app_mfa` (D7), which ships off like the others.
- **If the probe shows that it does not** (`Q5.verdict` is `other-session` or `no-session`): `app_mfa` is not built, API keys and apps keep acting without a second factor, and the public page keeps saying so (item 6 under "What stays open").
- **If the probe did not look** (`Q5.app` is `skipped`, or `Q5.verdict` is `unanswered` because the app token did not reach the probe function): the fact is not established and question 5 is still open. Neither branch is selected. The step of the probe that obtains an app token is run again, and until it gives one of the two answers above, `app_mfa` is neither built nor ruled out and the public page keeps the current sentence.

API keys and personal API tokens name no session and stay exempt from the second-factor rule in both branches.

The verdict is computed once per request. On PostgREST the pre-request function (D2) stores it in a transaction-local setting and every helper and policy reads that. On Storage and Realtime, which run no pre-request, the helpers compute it when the setting is absent, and policies read the refused set as `= any (array(select ...))`, the form `supabase/tests/0943_rls_benchmark_fixes.test.sql` already pins as one evaluation per statement. This matters because `private.person_capability_reach` runs per row through `has_capability`.

`app.my_org_auth_status` and `app.network_access` answer from the same verdict and gain `idle`, `network_allowed` and `blocked_reason`, so Atlas, the XOS API and Compass read one answer. Atlas's `xos-last-seen` cookie stops being the idle source. `private.require_second_factor` additionally requires a live session row.

### D2. PostgREST: a failing direct call is refused whole, with HTTP 401

`gate.pre_request()` is registered as `pgrst.db_pre_request` on the `authenticator` role. It lives in a new schema `gate` that is not exposed through the API and on which `anon`, `authenticated` and `service_role` hold usage. It cannot live in `private`: `0001_foundation.sql` line 37 revokes that schema from `anon` and `authenticated`, PostgREST calls the pre-request as the request role, and the lookup would fail for every request. pgTAP does not go through PostgREST and cannot catch that, so the registration is proven by a test over real HTTP (D8).

For `anon`, `service_role` and a request without a token the function returns before touching any table. For `authenticated` it distinguishes two kinds of call:

- **A direct call** carries no attestation (D3): Compass, a browser, a hand-made request, an API-key or OAuth token used directly. If the session is refused, or any organization the caller belongs to refuses it, the function raises SQLSTATE `PGRST` with HTTP status 401, code `XS401` and the reason as the hint. Nothing runs. **The strictest organization governs the whole call (owner decision 6).** The pre-request runs before the target organization is known, about 100 security definer functions identify the caller without the shared helpers (a text match, not a proof), and refusing whole is the only form that leaves none of the roughly 1,065 `app` functions open. It matches the XOS API's rule for a request bound to no organization (A69-010). HTTP 401 is the one shape that released Compass builds treat as "halt and wait for sign-in": queued writes are held, and a refused pull is an error, never an empty snapshot.
- **A server-mediated call** carries a valid attestation. It is not refused whole. The helpers (D6) drop the refusing organizations, so a person in two organizations keeps the one whose rules the session meets, and Atlas, Gateway and the API refuse before the handler from the same verdict.

A refused session can still reach what it needs to recover: `app.my_session_gate()` (new: each of the caller's organizations by name, and the reason it is closed), `app.my_org_auth_status`, `app.network_access`, `app.redeem_recovery_code`, `app.touch_my_session`, `app.my_sessions`, `app.sign_out_my_session`, `app.sign_out_my_other_sessions`, the break-glass start function of migration 1298, `app.ensure_my_profile`, and the `api_public` schema. The function reads the schema from the profile header PostgREST itself uses for the request method (`Accept-Profile` for GET and HEAD, `Content-Profile` otherwise); a test holds that a mismatched pair does not pass. A session refused as a whole reaches `api_public` only.

The probe reads the refusal's shape through the hosted gateway (`Q4.verdict`). `as-designed` leaves this decision as written. `status-only` (HTTP 401 without the `XS401` body) also leaves it standing, because released Compass builds read the status alone; the new Compass build then reads the reason from `app.my_session_gate` instead of the hint. `different` means the refusal does not arrive as HTTP 401: the PostgREST layer is then not enforced until this record is amended.

### D3. Our servers prove themselves with a signed attestation

Atlas, Gateway, Console, the XOS API and the Edge Functions that act for a signed-in person send one header on every PostgREST call: the person's address as Vercel reported it (`clientAddress`, the reader trusted today), a timestamp, the session id, and an HMAC over them with a server-only key. The database verifies it (five-minute window, bound to the token's `sub` and `session_id`). `createCallerClient` in `packages/data/src/client.ts` is the one place that adds it.

The key is `XOS_DATA_ATTEST_KEY`, and the owner approved it (owner decision 7):

- **The owner generates the key and enters it.** It goes into the Atlas, Gateway and Console Vercel projects as an environment variable, into Supabase as an Edge Function secret, and into Supabase Vault as the secret `xos_data_attest_key`, which the database's verifier reads. The steps are in `infra/runbooks/hosted-security-settings.md`.
- **No agent sees the value.** The repository names the variable and never holds a value for a hosted environment. Local and CI stacks generate a random value of their own when they start.
- **Its rotation waits for 5.0**, under the standing no-rotation decision of 2026-11-09. The verifier accepts two keys at once, so that rotation is a matter of adding the new key, deploying, and removing the old one, with no window in which calls fail.
- **Until the key is entered, no attestation verifies** and every call counts as direct. With every control off that changes nothing. The key is entered after packages 2, 7 and 8 have shipped to an environment and before the first control there is switched to observe.

If the build measures the Vault read above the budget in D9, the key moves to a table in `private` that only the verifier reads, and the owner enters it there instead.

Whoever holds the key can make a direct call look server-mediated and attest any address for a session token they already hold. Row-level security and the per-organization filtering still apply to such a call. The attestation never grants an identity.

The header depends on one hosted fact: that a custom request header reaches `request.headers` through the hosted gateway (`Q2.custom_header`). If the probe answers `altered` or `not-reached`, per-request attestation cannot work as designed, and packages 4 and 7 wait for an amendment of this record. Neither package starts before that answer is recorded (see "What builds in parallel"). The signed argument to `app.touch_my_session` (D4) does not depend on it, and neither does the verifier itself, which checks a signed value wherever it arrives.

### D4. The caller's address: attested, or a network pass, or the edge once the probe proves it

The allow-list needs an address the caller cannot write. There are three sources, in this order.

1. **Attested address**: on server-mediated PostgREST calls, checked on every request. Exact.
2. **Network pass**: `private.session_state` holds the last address at which the session was seen by one of our servers, and when. It is written only from an attestation, passed either as the header or as a signed argument to `app.touch_my_session`, never from a value the client supplies. A session passes the allow-list when its pass is inside the list and no older than five minutes. Compass obtains its pass by calling the XOS API (`POST /api/v1/session/network-pass`), which sees the device's address through Vercel. Live pages and long uploads send a heartbeat so a passive screen does not lose its pass.
3. **Edge address**: `private.request_ip()` on a direct PostgREST request, read at the place `xos.trusted_proxy_hops` names. `private.session_gate_config` holds the address source, `pass` or `edge`, and ships as `pass`.

The owner approved the probe (owner decision 2) and decided what follows from each answer (owner decision 3):

- **If the probe proves the hosted address chain** (`Q1.verdict` starts with `consistent`, and the person who ran it confirms that `Q1.own_address` is the public address they ran from): the owner sets `xos.trusted_proxy_hops` to the count the probe printed and approves switching the address source to `edge`. Direct PostgREST requests are then checked against the list on every request. The staging branch and production are separate projects behind the same platform, so before the switch on production, observe compares the edge address of each direct call that holds a fresh pass with the address of that pass, and the switch waits for those to agree.
- **If the probe does not prove it**: the address source stays `pass`. The allow-list on direct calls is the five-minute network pass, and the Security Overview states that limit in the words under "What the Security Overview can say". No direct call is refused merely because the chain is unproven.

Storage and Realtime use the pass, because Supabase documents no request header reaching the database there. The probe asks both (`Q3a`, `Q3b`). Where it finds the caller's address at a fixed place in a chain the client cannot move (`own_address_hops` is a number and `holds_when_spoofed` is `yes`), that path can be checked exactly, per Storage call or at each channel join and token renewal; otherwise it stays on the pass. Realtime Postgres Changes are evaluated by Realtime's change reader, not inside a request, and stay on the pass in every branch. Moving Storage or channel joins to exact enforcement changes what the database does; the public page's sentences for those paths change only through an amendment of this record.

**Compass is not exempt (owner decision 4).** Compass is refused outside an organization's listed networks, cellular and venue Wi-Fi included. An exemption could not be enforced in any case, because a caller declares its own surface. The Security settings panel in Atlas says so beside the allow-list switch before an Owner turns it on.

**API keys and OAuth app tokens are bound by the allow-list on the data endpoint (owner decision 9).** They have no session to hold a pass. Used directly against the data endpoint for an organization that enforces an allow-list, they are refused while the address source is `pass`, which is every case until the probe proves the chain, and checked per request on PostgREST once it is `edge`. On Storage and Realtime they stay refused for such an organization unless that path moved to exact enforcement. Through the XOS API they are checked on the attested address, as today.

### D5. Activity is recorded by the server, never claimed by the client

`private.session_state` (one row per session, removed with it) replaces the activity role of `private.session_devices`. The pre-request stamps it at most once a minute on read-write transactions; GET, HEAD and stable functions run read-only and cannot write, so a caller that only reads stays active through `app.touch_my_session` or through its token refresh. Released Compass builds never call touch; the Compass package adds it on foreground and on each sync cycle.

**One idle rule applies everywhere, Compass included (owner decision 5).** A device that is offline or unused for the organization's idle time signs in again. Two things come before `idle` is enforced anywhere:

- the Compass minimum version is raised to the build with the refusal screens and the activity touch (owner decision 12), so no released build that cannot stay active is still in use;
- the owner receives a proposal for a longer default idle time for field use, and decides it. The default stays 60 minutes until then, and `idle` is not switched to enforce before that decision. Package 9 writes the proposal from the idle gaps that observe records for Compass sessions.

### D6. Helpers, Storage and Realtime

- **Helpers.** `private.my_org_ids()`, `private.my_membership_ids()` and `private.person_capability_reach()` exclude the refusing organizations; `has_capability`, `capability_reach`, `orgs_with_capability` and `project_ids_with` inherit that. Their current bodies stay as `*_base` twins, used only by the recovery functions of D2 and by the read policies on `app.organizations` and on the caller's own `app.memberships`, so `/auth/mfa`, `/auth/session-ended`, `/auth/network-restricted` and the Compass gate can still name the organization. A catalog test holds that nothing else references a twin.
- **Storage.** One restrictive policy on `storage.objects`, all commands, to `authenticated`: the object's organization (`private.storage_object_org(bucket_id, name)` over the 13 buckets) must not refuse the session, and for a bucket whose path carries no organization the session must be refused by none. This closes the person-keyed buckets that hold organization files (imports, upload staging, support screenshots, deletion certificates).
- **Realtime, Postgres Changes.** A restrictive select policy on every table in the `supabase_realtime` publication, null-safe on `org_id`. Realtime evaluates table policies for each change with the subscriber's claims, so the verdict applies per delivered change. The policy filters and never raises, because the effect of an exception on Realtime's change worker is not established. The probe confirms that such a policy can read the claims the verdict needs (`Q3c.changes.claims` and `Q3c.changes.claim.session_id`); if it cannot, this policy waits for an amendment.
- **Realtime, broadcast and presence.** The same test is added to the `realtime.messages` policies through `private.ensure_realtime_channel_policies`. Realtime evaluates it at join and on each new token only. The anonymous live-link and showcaller rules are untouched.
- **Gateway and Console (owner decision 11).** Gateway refuses a member before the handler when the member's organization refuses the session, as Atlas does. Without that, the attested path would reach definer functions that check membership inline. External collaborators and Console support access stay outside organization rules, and the public page names them so.
- **Signed links.** Onboarding-upload links drop from 3,600 to 300 seconds (`packages/data/src/vendors.ts`).

### D7. Rollout: every control ships off, and the owner approves each switch

The owner decided the rollout (owner decision 1): the record is built with every control switched off, and the owner approves each switch to observe and then to enforce on production. No agent, migration or deploy changes a mode on production without that approval for that control.

`private.session_gate_config` holds a mode for each of six controls (`ended`, `mfa`, `lifetime`, `idle`, `network`, and `app_mfa` if the probe selects it): `off`, `observe` or `enforce`. `private.session_gate_orgs` sets a mode for one organization and one control, which overrides the global one, so enforcement starts with named organizations (the owner's own first). Both are read on every evaluation; a change takes effect on the next request with no deploy.

- **Off** (how every migration ships): the verdict is empty, the helpers and policies behave as today, and the pre-request returns after one single-row read. The pre-request registration is its own migration, applied last, because it runs on every request from the moment it lands.
- **Observe** (the owner approves it per control): nothing is refused. Each call that enforce would refuse writes one Postgres log line (`xos_session_gate`, with control, surface, organization and token type, and no personal data) and, on read-write transactions, a count in `private.session_gate_observations`.
- **Enforce** (the owner approves it per control), in this order: `ended`, `mfa`, `lifetime`, `idle`, `network`; `app_mfa` after `mfa`. Each needs at least seven days of observe on production showing no first-party path refused and no sign-in method issuing tokens without `session_id` or `amr` timestamps, then enforce on the canary organization, then everywhere. `lifetime` is announced first, because Compass sessions that have renewed past an organization's lifetime are refused the moment it turns on. `idle` and `network` wait for the Compass build and the raised minimum version (owner decision 12), and `idle` also for the owner's decision on the default (D5).

The apps are compatible with mode off (the attestation is ignored, the new status columns read as passing), so the database and the apps release and roll back independently.

Switching off has three levels, none of which needs a deploy: one control (`update private.session_gate_config`); the PostgREST layer (`alter role authenticator reset pgrst.db_pre_request` and `notify pgrst, 'reload config'`); and full removal (a down migration drops the restrictive policies and restores the helper bodies from the twins). The second level is rehearsed on staging before the registration migration reaches production. Switching a control off in an incident needs no prior approval; the owner is told at once.

### D8. Lockout protection and recovery

- **Second factor.** Setting `security.mfa_policy` to `admins` or `everyone` requires the setter's own session at `aal2`, so at least one Owner holds a working factor. Enrollment and verification run on Supabase Auth, which the gate does not touch, and the recovery functions and organization-name reads use the ungated twins, so a member who never enrolled can still enroll and a member can still redeem a recovery code.
- **Lifetime and idle.** Signing in again always restores access. The floors stay at 1 hour and 5 minutes.
- **Allow-list.** The existing guards stay (no empty list, plan feature, no enabling from an uncovered address, no removing the last entry while enforced). Break-glass at `aal2` from outside the list is honored inside the verdict and its start function is reachable by a refused session.
- **Compass in the field.** Released builds receive HTTP 401, which they already hold on. The new build shows which organization refuses and why, checks the gate before uploading media, and treats a Storage 403 under a refused session as "halt", not as a conflict.
- **Support.** `private.session_gate_overrides` suspends one control for one organization for at most 24 hours. It takes a secret key, an actor and a reason, is written to the audit ledger, and notifies the organization's Owners. The writer is `app.suspend_session_gate_control` and the early end is `app.end_session_gate_suspension` (migration 904190902; see "What package 3 hands to the packages after it").
- **The pre-request itself.** A defect in it is an outage of the whole data endpoint. It returns before any table access for `anon` and `service_role`, and level two of the switch-off removes it alone.

### D9. Performance budget

- Gate 17 stands: policy-filtered list queries under 50 ms at p95 on 1,000,000 rows, measured by `supabase/tests/0399_rls_benchmark.psql` with every control in enforce and a passing session. A plan-shape assertion in the style of 0943 holds that the refused set appears only as an InitPlan and that `person_capability_reach` reads the transaction-local verdict.
- The pre-request adds at most 3 ms at p95 to a PostgREST request in enforce (one session-state read, one `auth.sessions` read, the caller's memberships, one rules row per organization, one HMAC when attested, at most one single-row update a minute per session), and at most 0.5 ms in off. A new HTTP benchmark against a Postgres and PostgREST local stack measures both over 1,000 requests.
- Realtime evaluates the verdict per subscriber per change. The show-cue path is measured with 50 subscribers on one table before the Realtime package is enforced; the gate may add at most 5 ms at p95 to the policy check of one change for one subscriber.
- Creating a restrictive policy takes a brief exclusive lock. The Realtime installer applies one table at a time with `lock_timeout` and retries, outside show hours.

None of these was measured.

### D10. The access token lives 900 seconds

The owner decided to lower the access token lifetime from 3,600 to 900 seconds and to raise the Auth token-refresh rate limit in the same change (owner decision 8).

- **Why.** Broadcast and presence rooms re-check a session only at join and at each new token (D6). The token lifetime is therefore how long a session that stopped meeting a rule keeps receiving on rooms it already joined: 15 minutes instead of 60.
- **The rate limit.** Every session refreshes four times as often. Supabase Auth limits token refreshes per address, and Atlas, Gateway and Console refresh from Vercel's addresses for everyone. The limit is raised fourfold in the same change, from 150 to 600 refreshes per five minutes per address, so the number of sessions one address can keep alive does not fall. If the hosted value differs from 150 when the owner applies the change, the owner multiplies the hosted value by four.
- **In the repository** (package 12): `jwt_expiry = 900` and `token_refresh = 600` in `supabase/config.toml`, the pinned values in `infra/security/test/auth-config.test.ts`, and every text that states one hour for the access token.
- **On the hosted project** this is an Auth setting. The owner applies it, or approves a named person applying it, on staging and then on production, both values in one sitting. The location is in `infra/runbooks/hosted-security-settings.md`. It is applied when package 12 ships and not before, and the public page says 15 minutes only after it is applied on production.

Nothing else in this record depends on the shorter lifetime. Until it is applied, every "15 minutes" below reads 60.

## What stays open, and what the page must keep stating

1. **The allow-list is not exact on Storage and Realtime as Supabase documents them.** Those two services are not documented to give the database the address of a request. There the rule is: the same session was seen inside an allowed network by Atlas or the XOS API within the last five minutes. A token in use inside the network can therefore also be used from outside it on Storage and Realtime, and on direct REST calls unless the probe proves the edge address (owner decision 3). A member with any device inside the network can keep the pass alive. The page must say so.
2. **Broadcast and presence rooms** (co-editing, presence, budget, show cues) re-check a session only when it joins and when its token renews. A session that stops meeting a rule keeps receiving on rooms it already joined for up to one token lifetime: 15 minutes once D10 is applied on production, 60 minutes until then.
3. **Delete events.** Realtime does not apply row-level security to delete events; a connected session that is now refused can still receive the key of a deleted row.
4. **Bearer links.** Signed file links (at most 300 seconds after D6, and export links with their own lifetime) and single-use file-download tickets (2 minutes) work from any network and any session state until they expire. Profile media and organization brand assets are public.
5. **Idle means no recorded activity, not no human.** A client that keeps calling or refreshing stays active until the session lifetime ends. Only Atlas also measures human inactivity. The clock is one minute coarse.
6. **Apps and keys act without a second factor.** API keys, personal API tokens and OAuth apps have no lifetime or idle rule. An OAuth app is a public PKCE client: a person whose own session an organization refuses for lack of a second factor can still obtain an app token where a consent already exists, limited to that one organization and the capability groups granted, never Restricted data. The owner decided this is closed for OAuth apps if the probe shows an app token names its authorizing session (owner decision 10, control `app_mfa`). API keys and personal API tokens stay outside the second-factor rule in every case, and so do OAuth apps if the probe shows that the token names another session or none. A probe run that skipped the app token, or whose app token did not reach the probe, decides nothing (D1). Until `app_mfa` is enforced the page says that apps and keys act without a second factor; after it, the page says it of API keys only.
7. **People who are not members** (external collaborators in Gateway and Compass, recipients of a grant or a share) follow no organization's second-factor, session or network rule. Only the signed-out check applies to them. The owner confirmed this and that the page names it (owner decision 11).
8. **A person's own rows with no organization** (profile, preferences, own notifications) follow the signed-out check on server-mediated calls. On direct calls the strictest organization still governs.
9. **Support access through Console** follows Console's own rules and access transparency, not the organization's allow-list or second-factor policy. The owner confirmed this and that the page names it (owner decision 11). How support sessions reach rows was not read for this record and is confirmed in work package 7.
10. **Server-mediated calls rest on a server-held key** (D3).
11. **Workers, pg_cron and worker-minted tokens** act for an organization from Supabase's network and are outside all the rules by design.
12. **Supabase Auth's own endpoints** (sign-in, refresh, factor enrollment and verification) are not the data endpoint. A refresh still succeeds for a session an organization refuses; the refusal happens at the data call.
13. **Anonymous links and screens** (live links, showcaller screens, `api_public` token functions, kiosk device keys) carry no session.
14. **PowerSync** is not in production. Its replication role bypasses row-level security and it accepts a token by signature alone. Turning it on is blocked until its authentication calls the verdict.
15. **One customer's rule can stop another customer's crew in Compass.** On direct calls the strictest organization governs (owner decision 6), so a member of organizations A and B who is outside A's allowed networks, or cannot complete A's second factor in Compass (Compass verifies TOTP and recovery codes only), loses Compass for B too until that is resolved. External crew who are not members are unaffected.

What the probe was written to establish, each with the line that reads it and the part it decides: the hosted forwarded chain and hop count (`Q1`; exact allow-list on direct REST); whether a custom header reaches `request.headers` through the hosted gateway (`Q2`; per-request attestation, and the signed touch argument does not depend on it); what a Storage policy, a channel-join policy and a Postgres Changes policy can read on the hosted services (`Q3a`, `Q3b`, `Q3c`; exact allow-list on those paths, and the Postgres Changes policy); whether SQLSTATE `PGRST` yields exactly HTTP 401 through the hosted gateway (`Q4`; Compass's safe behavior); the claims of an OAuth app token (`Q5`; `app_mfa`, which stays undecided for as long as that question is skipped or unanswered). The staging run of 2026-11-21 established `Q1`, `Q2`, `Q3a`, `Q3c` and `Q4` on the staging branch ("Work package 0"). Still not established: what a channel-join policy can read on the hosted service (`Q3b`), the claims of an OAuth app token (`Q5`), and every one of these on production, which is a separate project behind the same platform (D4). Outside the probe: whether supabase-js surfaces that 401 unchanged (package 9's tests); whether every sign-in method issues `session_id` and `amr` timestamps (observe measures it); the claims of the three worker-minted tokens (package 8 reads the functions); the hosted Auth session settings (the owner reads the dashboard when applying D10).

**Asking for the verdict once per request.**

- The pre-request (package 4) calls `private.session_verdict_store('postgrest')` once and then reads `private.session_direct_refusal()`. A call with `(select verified from private.request_attestation())` true is server-mediated and is not refused whole. For a refused direct call it lets through what `private.session_gate_reachable(<schema of the profile header>, <function name or NULL>, private.session_refusal() is not null)` allows and raises SQLSTATE `PGRST` for the rest, with a JSON message whose `code` is `XS401` and whose `hint` is the reason; `supabase/tests/904189901_direct_endpoint_attack_postgrest.test.sql` reads exactly those two fields. On a read-write transaction it calls `private.stamp_session_activity()`. `gate.pre_request()` is a security definer function, because the request role holds no usage on `private`; storing the verdict and recording observe both work on a read-only transaction.
- Helpers and policies (packages 3, 5 and 6) read `private.session_refusal() is null` and `org_id <> all (array(select private.session_refused_org_ids()))`. The array form is one InitPlan for each statement (the verdict suite holds the plan shape). They never call `session_verdict_compute`. Where no pre-request ran, the readers compute the verdict themselves, with the network pass as the address.
- A package that asks on another surface and wants observe recorded calls `private.session_gate_observe('<surface>', private.session_verdict())` from a volatile context. The stable readers log nothing, so a policy evaluated for every delivered change does not flood the log.

**No request waits on another for the gate's own records.** Two rows are written inside a caller's request and stay locked until its transaction ends: the observation counter, which every observed read-write call of one organization, control, kind of token and reason shares, and the session's row in `session_state`. Both are written only under a transaction-scoped advisory lock that is tried and never waited for (`private.session_gate_lock_key`).

- `private.session_gate_observe` skips the count of a row another request is writing. The `xos_session_gate` log line is written for every call and is the complete record; `calls` is a lower bound under contention. Seven days of observe are read from the log lines where the exact number matters.
- `private.stamp_session_activity` reads the session's row without a lock and returns when the last recorded activity is under a minute old and the pass would not change. Otherwise it tries for the lock and returns when another request of the session holds it, because that request records the same activity. A pass carried by the skipped call is not written; the next call or touch that carries an attestation writes it.
- **The network pass is as old as its attestation.** `pass_at` is the time the server signed, never later than now, so the pass ends five minutes after the server saw the address (D4), however late or often the attestation is presented. An attestation older than the stored pass changes nothing, so a replay cannot extend a pass or move it back to an earlier address. Two attestations signed in the same second for different addresses keep the first one written.
- `infra/db/test/session-gate-concurrency.sh` holds this on two connections against a local stack, after the pgTAP suites in CI; pgTAP runs on one connection and cannot.

**What package 1 handed on, decided.**

1. _The automation worker's token._ The verdict treats a token with the claim `xos_origin` = `worker` as outside every rule. The token as it is minted today carries no such claim and no `session_id`, and with `ended` in enforce it is refused `session_ended`. The verdict suite pins both. Package 8 adds the claim to the three minting functions and to the test token of `1481_automation_runs.test.sql`, and `ended` is not enforced before that.
2. _API-key tokens._ The kind of token is decided before any amr timestamp is read, so a key token with timestamp 0 or with none is exempt from the signed-out, second-factor, lifetime and idle rules and bound by the allow-list. The verdict suite pins both forms.
3. _A deleted account's token._ `app.delete_my_account` is not on the list a refused session reaches. A signed-out token must not be able to delete an account on a direct call, and the list cannot tell the replay of a finished deletion from a first call. On a direct call with `ended` in enforce the replay is refused with HTTP 401; through our servers, which are not refused whole, it still answers with the stored result. `1112_account_deletion.test.sql` is unchanged, and the verdict suite pins the refusal and the list.

## Test plan

**The attacker's test.** Four files, one per surface so that the packages that build in parallel never edit the same one: `supabase/tests/904189901_direct_endpoint_attack_postgrest.test.sql`, `904189902_direct_endpoint_attack_storage.test.sql`, `904189903_direct_endpoint_attack_realtime.test.sql` and `infra/db/test/direct-endpoint.http.test.ts`. All four are written in package 2, before the gate, and fail today. Each case signs in as a member of an organization that sets the rule and calls the data endpoint directly:

- an `aal1` session under `mfa_policy = everyone` reads a project list, inserts a record, calls a definer function that reads `app.memberships` inline (`app.workforce_directory`), reads and writes an object in the imports bucket, and joins a private channel;
- the same five actions with a session older than `session_hours`; with a session whose last activity is older than `idle_timeout_minutes`, including a touch sent after the timeout; with a session whose `auth.sessions` row was deleted, including a step-up function at `aal2`; and from an address outside the allow-list, with a session token and with an API-key token;
- a token with no `session_id` claim.

Today every case succeeds, so every assertion that it is refused fails. The cases land marked as expected failures (pgTAP `todo`, and `test.fails` in the HTTP file), and each package removes the marks in its own file for what it closes: package 4 in the PostgREST file and the HTTP file (HTTP 401, code `XS401`, the right hint), package 5 in the Storage file, package 6 in the Realtime file. Package 10 holds that no mark is left in any of the four, by a check that reads them. The HTTP file repeats the PostgREST cases over a real PostgREST, because pgTAP cannot see the pre-request registration.

**pgTAP, per package.** The passes: an organization on defaults; `aal2`; break-glass at `aal2` from outside the list; a non-member; `service_role`; no token; an API key (exempt from three rules, bound by the allow-list); a worker claim; an attestation that is valid, expired, for another session, or signed with another key. Two organizations in one session: a direct call is refused when one refuses; an attested call returns only the admitting organization's rows. Recovery: a refused session reads its organization's name, `app.my_session_gate`, redeems a recovery code, starts break-glass, lists and signs out sessions. Modes: off changes nothing (the existing suites stay green), observe records and refuses nothing, an organization row overrides the global mode, an override suspends one control and expires. Catalog: every published table has the restrictive policy; `storage.objects` has it; only the listed functions and policies reference a twin; `private.request_ip` and the attestation verifier are the only readers of forwarding headers; `gate.pre_request` is executable by `anon` and `authenticated`; a profile-header mismatch does not reach the allow-list. If `app_mfa` is built: an app token whose authorizing session is `aal1` is refused for an organization that requires a second factor and passes for one that does not.

**Unit and end to end.** `packages/data` (attestation, `orgAuthDecision` with idle and network from the database); `packages/api` (idle and network refusals, the network-pass route); `packages/sync` (`XS401` with status 401 is `unauthorized`); Compass (a refused organization never reaches `session.replace`; queued writes with media halt); Playwright a77 and a99 (the redirect pages with a refused session, and a direct REST call from the page context for each rule).

**Staging, with the owner's approval of each step.** The probe (approved); then real tokens against REST, Storage (a TUS upload and a signed link) and Realtime (Postgres Changes and a private channel) for each control, inside and outside a listed network; a released Compass build and the new build against enforce; the level-two switch-off.

## What the Security Overview can say

The owner decided the rule (owner decision 13): the page changes one control at a time, only after that control is enforced and verified on production, never at merge, and in the sentences below. Lines 39 and 40 keep their current text until then. Each sentence names people who are not members and support access where it applies (owner decision 11).

**After `ended` is enforced (packages 2 to 6):** "Each person sees where they are signed in and can sign out any other session or all of them at once. Atlas, Gateway, the XOS API and the underlying data endpoint stop accepting a signed-out session on its next request."

**After `mfa` and `lifetime` are enforced:** "Per-organization session lifetime and second-factor requirement: these are enforced in the database on every call to the underlying data endpoint (REST and Storage) and on every live update delivered, as well as in Atlas, the XOS API and Compass. **After `idle` is enforced (needs packages 8 and 9, the Compass minimum version, and the owner's decision on the default):** add "The idle timeout is enforced the same way, in Atlas, the XOS API, Compass and on direct calls. ## Alternatives rejected

- **Gate tokens** (the data endpoint accepts only 120-second tokens that Atlas or the API minted). Rejected: a token is issued even when every organization refuses the session, which leaves every definer function with an inline membership check and the person-keyed buckets open; it makes one Edge Function and one key a single point of failure for all data access; it has no per-organization rollout; and Realtime clients that miss a two-minute renewal are disconnected. Its two strongest ideas are kept: the address is attested by a server that sees it (D3, D4), and a refused session can ask which organization refuses it (D2).
- **Verdicts stamped in the token at issue.** Rejected: a refused organization's rows go missing without an error, which makes released Compass builds delete local data and turn queued writes into conflicts; a token without `session_id` is exempt, which fails open; the hook becomes a write path on every sign-in; and a 300-second token lifetime collides with Supabase Auth's per-address refresh limit. Kept from it: the verdict computed once per request into a transaction-local setting, and a token refresh counted as activity.
- **Routing all data access through the API** (the plan in ADR 0033). Rejected as the way to close the gap: Vercel functions cannot carry Realtime websockets or the upload chunks, and Compass would lose offline-first sync.
- **Supabase's own session time-box and inactivity timeout.** They are project-wide, not per organization, and are enforced only at the next refresh.
- **A restrictive policy on every table with `org_id`.** Rejected for this release: an exclusive lock on about 800 live tables for a path the pre-request already refuses whole. It is limited to the published tables, where Realtime needs it.
- **Judging each organization separately on direct calls.** The owner chose the strictest organization instead (owner decision 6). Per-organization judgment needs an audit of about 1,065 functions and two to three more weeks, and leaves any function the audit misses open.
- **Refusing every direct REST call for an organization with an allow-list when the chain is unproven.** The owner chose the five-minute pass instead (owner decision 3), because the refusal would stop Compass for those organizations.
- **Keeping the access token at 3,600 seconds.** The owner chose 900 (owner decision 8); 3,600 would leave rooms open to a refused session for an hour.

## Consequences

- Row-level security reads session state for the first time. The header of migration 1330 ("Row level security does not read these settings") stops being true when package 3 lands.
- The three helpers at the root of about a thousand policies are redefined. A defect there is a production-wide outage or leak; mode off, the benchmark and the full pgTAP run before each step are the guard.
- A new server secret exists. The owner creates it and stores it in three Vercel projects, a function secret and Vault; nobody else holds it; it is first rotated at 5.0.
- Every session refreshes its token four times as often once D10 is applied, and the refresh rate limit is four times as high.
- Compass needs a store release and a raised minimum version before `idle` and `network` are enforced, and from then Compass stops outside an organization's listed networks.
- Customers who call PostgREST directly with an API-key token from outside their listed networks are refused once `network` is enforced, and from any network while the address source is `pass`.
- Hosted changes, all of them the owner's and none made by this record or by an agent: running the staging probe, entering `XOS_DATA_ATTEST_KEY` in Vercel and Supabase, `xos.trusted_proxy_hops`, the token lifetime and refresh limit, and every switch of a control to observe or enforce on production.
