# ADR 0031: Gate 5 Handler Completion: Retired Operations and New Tables

- Status: Proposed (amends ADR 0023)
- Date: 2026-10-19
- Decider: Orchestrator (proposed by A50, RRR-94)

## Context

Section 18 gate 5 requires a handler and a contract test for every documented operation. After Wave 6, 232 operations had no handler, mostly because their frozen v1 shape could not be filled faithfully from the schema. ADR 0023 lets a module agent correct a frozen shape while v1 is a draft. Some operations have no faithful shape at all: no table backs them, or no caller of the public API can write their table under row level security. For each of those, this ADR records whether the operation was retired through a correction or whether a table was built for it.

Corrections that only change a shape so a handler can serve it are entries in the module files under `packages/api/src/catalog/modules/` and are not repeated here.

## Decision

### Retired operations

| Operation                                                                                                                                                     | Correction                              | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `moderationActions.create`                                                                                                                                    | `moderation-action-platform-decision`   | `app.moderation_actions` (0720) is append-only and written only by the platform: tenants have a read policy and no insert policy. A Digital Services Act decision belongs to the platform, never to the organization that posted the listing. Section 4.10 places the moderation queue in the internal platform operator console, which uses the platform operator session (`private.is_platform_operator`, 0643), not the public API. The Section coverage entry for abuse reports now lists `moderationActions.list` and `.get`. |
| `onboardingItems.update`                                                                                                                                      | `onboarding-item-submission`            | `app.onboarding_items` (0730) grants insert of the engagement and requirement only and no column update but `deleted_at`. The document and submission time are written by `app.submit_onboarding_item`, which only the engaged party may call. The correction replaces the update with the action `onboardingItems.submit`, which calls it.                                                                                                                                                                                        |
| `shipments.transition`                                                                                                                                        | `shipment-carrier-and-window`           | `app.shipments` (0351, 0440) has no lifecycle column. A shipment's progress is recorded by its dock check-in, gate release and marshalling log entries (journey 20), which have their own operations. Building a shipment lifecycle would duplicate those facts (Section 3.15), so the transition and the `shipment_state` field are retired.                                                                                                                                                                                      |
| `memberships.update`                                                                                                                                          | `membership-validity-through-rpcs`      | `app.memberships` (0202) grants callers no update. `valid_to` is set only by `app.end_membership` and `app.leave_organization`, which also open the offboarding checklist (0861); `memberships.end`, `.offboard` and `.leave` serve them.                                                                                                                                                                                                                                                                                          |
| `projectAssignmentRoles.list`, `.get`, `.create`, `.delete`                                                                                                   | `project-role-on-assignment`            | Project assignments are `app.project_members` (0301), one row per membership and project, carrying its `project_role`. There is no `app.project_assignment_roles` table. Section 4.8.1 asks for several project roles on one project; the schema holds one per assignment, and changing that means reworking every project-scoped policy (`private.project_ids_with`). That gap is recorded here for a later schema change, not papered over with an API resource that has no table.                                               |
| `accountMemberships.update`                                                                                                                                   | `account-membership-through-rpc`        | `app.account_memberships` (0710) grants callers no update. A membership ends through `app.end_account_membership` (`accountMemberships.delete`), and its roles change through `accountMembershipRoles`. `accountMemberships.create` is served through `app.add_account_member`, with the first role in the body.                                                                                                                                                                                                                   |
| `representations.update`                                                                                                                                      | `representation-terms-accepted`         | `app.representations` (0710) grants callers no update. Scopes and expiry are what the artist accepted, so changing them without a new acceptance would extend an agency's reach beyond the artist's consent. A change revokes the representation and proposes a new one.                                                                                                                                                                                                                                                           |
| `verifiedDomains.verify`                                                                                                                                      | `verified-domain-service-check`         | `app.record_domain_verification` (0850) is granted to the service role only, and `guard_org_domain` refuses any other change to the verification fields. The platform verification service checks pending domains.                                                                                                                                                                                                                                                                                                                 |
| `profileSections.list`, `.get`, `.create`, `.update`, `.delete`                                                                                               | `profile-sections-are-visibility-rules` | Sections are the fixed list `app.profile_section` (0860). A section's own visibility, never higher than the profile's, is `app.profile_visibility`, served as `profileVisibilityRules`. A `profile_sections` table would store the same visibility twice (Section 3.15).                                                                                                                                                                                                                                                           |
| `profileHandles.list`, `.get`, `.create`, `.update`                                                                                                           | `profile-handle-on-profile`             | A handle is a column of `app.person_profiles` and `app.organization_profiles` (0860), issued with the profile and changed under `guard_handle` (once every 30 days, with a 90-day redirect). The correction adds `handle` and `handle_changed_at` to `personProfiles` and `organizationProfiles`, where the handle is changed.                                                                                                                                                                                                     |
| `verifications.create`                                                                                                                                        | `verification-recorded-by-provider`     | `app.organization_verifications` (0860) grants callers no insert. Section 4.8.3 shows a badge only after the platform or a provider checks the claim, and those record it with the service role.                                                                                                                                                                                                                                                                                                                                   |
| `blocks.list`, `.get`, `.create`, `.delete`                                                                                                                   | `blocks-not-offered`                    | No table backs blocks. Section 7.3 names a `blocks` table, but Sections 4 and 6 never define what a block hides or where it is enforced. An endpoint that stores blocks nothing enforces would tell a person they are protected when they are not. The operations leave v1 until blocking is specified and enforced.                                                                                                                                                                                                               |
| `canonProductionTemplates.list`, `.get`                                                                                                                       | `canon-production-template-private`     | `xpms.production_template` (0105) holds real-world rows, and 0199 grants tenants no read on it until the owner approves publishing it (ADR 0014 owner decision 8). The operations return, additively, once it is published.                                                                                                                                                                                                                                                                                                        |
| `canonSupersessions.get`                                                                                                                                      | `canon-supersession-by-domain`          | `xpms.supersession` (0101) is keyed by code domain and code, and one code can be superseded in two domains, so no single path key identifies a row. The list orders by domain and code and filters on both.                                                                                                                                                                                                                                                                                                                        |
| `canonIntake.list`, `.get`, `.create`                                                                                                                         | `canon-intake-not-tenant-proposals`     | `xpms.intake` (0101) is the canon pipeline's staging of Playbook and Bible cells awaiting an owner decision, not tenant proposals. An org proposes canon through `canonExtensions.propose` (`app.canon_extension_proposals`, 0490), which shares the CanonIntake shape.                                                                                                                                                                                                                                                            |
| `subscriptions.update`                                                                                                                                        | `subscription-plan-through-billing`     | A plan is paid for. `app.sync_subscription_from_stripe` (0560), granted to the service role only, is the one path from a Stripe subscription to `app.subscriptions`. Writing `plan_code` directly would grant a plan nobody paid for.                                                                                                                                                                                                                                                                                              |
| `orgLegalEntities`, `orgIpAllowlistEntries`, `accessReviewCampaigns`, `accessReviewItems`, `breakGlassSessions`, `projectShares` (every operation, 26 in all) | `settings-features-not-built`           | No table or behavior exists for any of them, only setting definitions (0851). Sections 4.5 and 8.4 give them enforcement: the allow-list refuses other addresses, break-glass needs MFA, a one-hour limit and an Admin notice, reviews remove unreviewed access, and shares open a project to a partner. A table without that enforcement would report protection that does not exist. These are spec features still to build; each returns to v1, additively, when it ships.                                                      |

### Tables built

| Table             | Migration | Operations                                                 | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------- | --------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app.price_books` | 1170      | `priceBooks.list`, `.get`, `.create`, `.update`, `.delete` | Section 7.3 lists `price_books` under money and formats, and the v1 contract documents an org price book for selling items, read with `procurement.catalog.read` and written with `procurement.catalog.write`. No table backed it. The table holds the name and the currency (`currency_code`, correction `price-book-currency-code`); a name appears once per org among live books, and delete is soft. Prices within a book are left to a later additive resource, since the frozen contract has none. |

## Consequences

- Still to build, as features rather than handlers: legal entities, the IP allow-list, access reviews, break-glass, project shares, several project roles per assignment (Section 4.8.1) and blocks. Each needs its schema, enforcement and UI, and its operations return to v1 additively once it exists.

- The Playbook library mirrors, the Roles Library (`xpms.role`) and the canon labor rate cards (`xpms.rate_card_resolved`), which ADR 0023 left for the canon owner, are served in the shapes of their tables. Their columns are fixed by the import (Section 2.1), so the open owner decisions of ADR 0014 change their values, not their shapes.

- The retired operations leave `/v1` while it is a draft, so the published document never offers an operation that every caller is refused.
- The resource coverage list (`packages/api/src/catalog/coverage.ts`) follows the retirements.
