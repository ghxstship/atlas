# Secure Development Policy

> **Draft for review by counsel before launch.** This internal policy is a draft. It takes effect when the Owner approves it, and its effective date is that date of approval.

## 1. Purpose and Scope

This policy sets the secure development life cycle for XOS 4.0 at GHXSTSHIP Industries LLC ("GHXSTSHIP"). It applies to every change to the monorepo, whoever makes it: employees, contractors, open source contributors and AI coding agents.

## 2. Standards

- **Verification standard:** OWASP Application Security Verification Standard 5.0, Level 2. Every requirement is mapped to a test or document in `legal/security/asvs-matrix.md`.
- **Threat classes:** the OWASP Top 10 and the OWASP API Security Top 10.
- **Authentication:** NIST SP 800-63B.
- **Accessibility:** WCAG 2.2 Level AA is a release requirement, not an afterthought.

## 3. Design

- **The database is the boundary.** Authorization, tenancy, state transitions, gate criteria, money rules and refusal semantics are enforced in Postgres. New tables ship with row-level security enabled and policies tested in pgTAP before any feature uses them.
- **One API contract.** Every mutation has a public API operation defined by Zod schemas that generate the OpenAPI document.
- **Threat modeling.** New features that add a trust boundary, external access path, file handling or integration are threat-modeled before implementation. The independent security reviewer keeps the platform threat model current.
- **Data classification.** Every new column is classified in the column registry. Restricted columns use field-level encryption and masking from the start.
- **Privacy by design.** New processing of personal data is assessed against the records of processing, and a DPIA is completed where the processing is high risk.

## 4. Implementation Rules

- TypeScript in strict mode everywhere, with `noUncheckedIndexedAccess`.
- Validate all input with shared Zod schemas at the boundary.
- No raw SQL strings in application code outside migrations and stored procedures.
- Parameterize every query. Encode every output for its context.
- Strict Content Security Policy with nonces; same-site cookies; CSRF protection on server actions.
- SSRF protection through an allow-list resolver for webhooks and imports.
- Uploads are MIME-sniffed, size-capped, virus-scanned and SVG-sanitized; active content is never served inline from public buckets.
- No silent catches. Every error path recovers, surfaces a typed error or returns a refusal.
- No secrets in code, configuration files or logs.
- No unfinished-work markers, filler copy or test doubles in production paths; the finish guard enforces this.

## 5. Review and Testing Gates

Every pull request must pass, before merge:

1. Typecheck, lint and format.
2. The finish guard.
3. Unit tests, with 85 percent line coverage on the schemas, data and API packages.
4. pgTAP suites for row-level security on every table, including cross-tenant, anonymous and role-band attempts, every invariant and every state machine transition.
5. API contract tests for every operation.
6. CodeQL and Semgrep static analysis, dependency audit, secret scanning, license check, and Supabase database advisors with zero errors.
7. Migration checks: apply cleanly from empty, and generated types up to date.
8. An OpenAPI breaking-change check against the last release.
9. Review and approval by a maintainer of the paths changed. The author cannot approve their own pull request.

A dynamic scan (OWASP ZAP baseline) runs against staging on every deployment to staging. Findings rated High or Critical block release.

## 6. Supply Chain

- The lockfile is enforced; installs are frozen in CI.
- Dependencies are pinned and updated by automated pull requests, reviewed like any change.
- GitHub Actions are pinned by commit hash.
- Commits on `main` are signed.
- Each release ships a CycloneDX SBOM.
- New dependencies are reviewed for maintenance health, license and security history.

## 7. Environments and Test Data

- Development, staging and production are separate, with separate credentials.
- Production data is never copied to development or staging. Test data is synthetic, generated by seed scripts.
- AI coding agents work in isolated worktrees without production credentials.

## 8. Vulnerability Management

| Severity | Fix target from confirmation |
| -------- | ---------------------------- |
| Critical | 7 days                       |
| High     | 30 days                      |
| Medium   | 90 days                      |
| Low      | Next planned release         |

Vulnerabilities come from scanners, the independent security reviewer, dependency advisories and researcher reports under the Responsible Disclosure Policy. Each is tracked as an issue with a severity and owner.

## 9. Training

Everyone who changes code completes secure coding training at onboarding and every year, covering the OWASP Top 10, row-level security patterns and this policy.

## 10. Review

This policy is reviewed at least once a year and when the verification standard changes.
