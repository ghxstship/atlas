# A69-003: The allow-list judged the address the client wrote

## Finding

`clientIp` in the API runtime and in Atlas (`lib/auth/legal.ts`) returned the first `X-Forwarded-For` entry. Atlas
passes that address to `app.network_access` when it resolves a member's org (pages, server actions, the proxy route
guard) and when someone turns the list on; the API authenticator passes it before any handler runs. The browser error
route keyed its rate limit on the same entry.

On Vercel the platform replaces the header with the one address it saw, so the first entry is the client there. Behind
any proxy that appends instead, which is what nginx (`proxy_add_x_forwarded_for`), Caddy, Traefik and the Kong gateway
of the self-hosting guide do, the first entry is whatever the client sent.

## Impact

On a self-hosted deployment, a member outside the org's allowed networks who sent `X-Forwarded-For: <office address>`
passed the IP allow-list in Atlas and the API. The legal acceptance log stored the claimed address, and the browser error
limit reset on every report.

## Fix

`@xos/data/client-address` reads the entry the nearest trusted proxy appended, counted from the right past
`XOS_TRUSTED_PROXY_HOPS` (0 by default, right on Vercel and behind one proxy; 1 behind a CDN and a proxy). A chain
shorter than the trusted hops is unknown, which an enforcing allow-list refuses. `X-Real-IP` counts only without a
chain. Atlas, the API authenticator (`trustedProxyHops`) and the legal acceptance log use it; the browser error limiter
keys on the last entry. The setting is documented in the Atlas environment, the self-hosting guide and the hosted
runbook.

## Test

The client address, API authenticator, Atlas and client-error suites pin the last entry, the hop count and the short
chain; an outside address that names an allowed one first is refused for sessions and API keys. The Semgrep rule
`xos-forwarded-for-first-entry` refuses new code that reads the first entry.
