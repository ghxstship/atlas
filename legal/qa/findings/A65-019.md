# A65-019: Doctrine 3.4 does not hold in the canon data

## Finding

Section 3.4: "Every gated phase must carry at least one Active element or a declared gap." On a fresh reset
`xpms.v_phase_coverage` reports:

| Phase        | Active elements |
| ------------ | --------------- |
| SCP (gate 1) | 0               |
| ENG (gate 2) | 0               |
| ADV (gate 3) | 26              |
| PRC (gate 4) | 149             |
| BLD (gate 5) | 81              |
| INS (gate 6) | 30              |
| OPR (gate 7) | 118             |
| AMP (gate 8) | 0               |
| CLS (gate 9) | 0               |

There is no declared-gap record: a correction in `packages/api/src/catalog/modules/canon.ts` removed the
`declared_gap` field because the view declares none.

## Why it matters

The coordinate matrix and phase coverage reports show four empty phases with no stated reason.

## Suggested fix

The owner either binds elements to those phases in the canon (ADR 0014 open decision 7 covers unstated
relationships) or ratifies declared gaps. Engineering then adds an `xpms.declared_gap` governance table with a
ratifier, exposes it in `v_phase_coverage`, and adds the pgTAP above.

## Resolution (owner decision 39, WP18)

The owner ratified Scope, Engage, Amplify and Close as declared gaps (ADR 0033 decision 39); their catalog items keep
the Proposed state the Item Catalog gives them. `xpms.declared_gap` holds each gap with its reason, the decision and
the ratifier, seeded by the canon importer from `canon/rulings/decision-39.yaml` (migration 1610 for staging).
`xpms.v_phase_coverage` reports `declared_gap` and `declared_gap_reason`, and API v1's `canonPhaseCoverage` serves
`declared_gap` again with the reason (correction `canon-phase-coverage-columns`). The importer stops when a gated
phase has neither an Active element nor a declared gap, and reports a declared gap on a phase that has one.
