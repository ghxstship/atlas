# A47-001: Playbook field targets in app do not resolve

## Finding

Section 18 gate 14 asks that "every `field` target exists in the schema and the OpenAPI document".
The column map gives 823 Playbook columns the `field` disposition. The 259 that land in the Standard
Library and Production Template (`xpms.*`) all resolve, because those tables are generated from the
map. Of the 564 that land in the domain schema (`app.*`), 455 name a column that no migration
creates. They were written as `<entity>.<column key>` skeletons before A03 built the domain tables
(for example `app.access_grid.access_point`, while `app.access_grid` has `zone_id`,
`credential_category_id` and `access_level_enum_id`), and nobody reconciled them afterwards.

Measured against `packages/data/src/database.types.ts` on main e40eddf. The same query against a
database (`xpms.playbook_column` joined to `information_schema.columns`) gives the same 455.

## Why it matters

The round trip (pgTAP 0109) passes because it exports the Production Template from xpms, not from
the domain tables, so it cannot see the drift. A Playbook import into a live project, the
Playbook export of a project, and Section 20.1 item 7 ("every row and column of all 45 Playbook
sheets is present in canon, the Standard Library or the Production Template") all depend on each
domain column knowing where it lands.

## Suggested fix

For each unresolved target, either point it at the real column (often a foreign key: `vendor` to
`vendor_id`, `department` to a canon code column), mark it `computed` with its source, or mark it
`presentation` with the reason. Lower the count in `canon/import/test/field-targets.test.ts` as
each table is reconciled, and delete the ledger when it reaches zero. Where a Playbook column has
no home and should have one, the owning module agent adds the column with an ADR 0023 correction.

## Reconciled (A51, RRR-96)

Count before: 455 unresolved domain targets. Count after: 18, every one blocked on an owner ruling. Each
of the 455 entries in `canon/map/playbook-columns.yaml` now carries a transform that states its disposition, and
the generated seed (`0150_xpms_canon_seed.sql`, `xpms.playbook_column`) carries the same text. Every disposition
stays `field`, so the round trip is unchanged: 0 unexplained differences.

### Blocked on owner

Each needs a canon ruling of the kind RRR-64 holds (Section 2.1: neither file silently wins). None is invented here.

- **Status labels that are not states of the target lifecycle** (RRR-64, the 32 enumeration labels that are not
  Bible states; the Playbook's Workflow Status enumeration): Asset Inventory STATUS (Active), Budget Expenses
  STATUS (Open, Estimated), Marshalling Yard Log STATUS (Staged), Projects OPERATIONAL STATE (Scheduled), Work
  Orders STATUS (Completed, Scheduled), Crew Shifts STATUS (Confirmed), Shipping Manifest STATUS (Scheduled).
- **Landlord counterparty type** (RRR-64): Budget Expenses VENDOR.
- **Enumeration labels that differ from the Standard Library**: Change Orders CHANGE ORDER TYPE (Scope Addition
  against Order Type Scope Expansion), Shipping Manifest FREIGHT TYPE (Ground Freight).
- **Labels that are not canon codes**: Production Schedule ACTIVITY TYPE (not a record kind), Work Orders WORK
  ORDER TYPE (not a record subtype), Staffing Requisition EVENT PHASE (not one of the nine phases), Locations
  DEPARTMENT, CATEGORY and SUB CATEGORY (not canon departments or categories, so no space URID can be assigned).
- **Priority**: Production Tasks PRIORITY and Work Orders PRIORITY. Records have no priority, and the only
  library list is Incident Priority with different labels.

These should be added to RRR-64. When the owner rules, the entry gets its column (or value mapping), the count in
`canon/import/test/field-targets.test.ts` drops, and the finding closes at zero.

The OpenAPI half of gate 14 (every field target reachable through an operation) is still not measured.
