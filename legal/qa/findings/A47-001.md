# A47-001: Playbook field targets in app do not resolve

## Finding

Section 18 gate 14 asks that "every `field` target exists in the schema and the OpenAPI document".
The column map gives 823 Playbook columns the `field` disposition. The 259 that land in the Standard
Library and Production Template (`xpms.*`) all resolve, because those tables are generated from the
map. Of the 564 that land in the domain schema (`app.*`), 455 name a column that no migration
creates. They were written as `<entity>.<column key>` skeletons before A03 built the domain tables
(for example `app.access_grid.access_point`, while `app.access_grid` has `zone_id`,
`credential_category_id` and `access_level_enum_id`), and nobody reconciled them afterwards.

Measured against `packages/data/src/database.types.ts` on main e40eddf. The same query against a
database (`xpms.playbook_column` joined to `information_schema.columns`) gives the same 455.

The OpenAPI half of the check (every field target reachable through an operation) is not
measured; it depends on the reconciled targets.

## Why it matters

The round trip (pgTAP 0109) passes because it exports the Production Template from xpms, not from
the domain tables, so it cannot see the drift. A Playbook import into a live project, the
Playbook export of a project, and Section 20.1 item 7 ("every row and column of all 45 Playbook
sheets is present in canon, the Standard Library or the Production Template") all depend on each
domain column knowing where it lands.

## Suggested fix

For each unresolved target, either point it at the real column (often a foreign key: `vendor` to
`vendor_id`, `department` to a canon code column), mark it `computed` with its source, or mark it
`presentation` with the reason. Lower the count in `canon/import/test/field-targets.test.ts` as
each table is reconciled, and delete the ledger when it reaches zero. Where a Playbook column has
no home and should have one, the owning module agent adds the column with an ADR 0023 correction.
