# A54-001: Invariant 8 covers secrets the schema does not hold

## Finding

Section 7.5 invariant 8 says: "Access codes, second factors, recovery codes and kiosk PINs are stored hashed and
shown once." The migration 1220 registry gives it the code `inv_08_token_rpcs_hashed_secrets`, and pgTAP covers the
parts the schema holds:

- invite tokens: only the SHA-256 is stored, they expire, and they lock after 5 mismatches (0206)
- agreement signing tokens and access codes: bcrypt hashes, a 90-day limit, locking at 5 (0361)
- kiosk PINs: bcrypt hashes that are never selectable, locking after five wrong PINs (0340)
- token RPCs are rate limited (`private.rate_limit_exceeded`, 0510)

Two of the four named secrets have no home in our migrations:

1. **Recovery codes.** No table, function or screen issues MFA recovery codes. The only mention in the repository
   is the spec sentence above.
2. **Second factors.** TOTP, phone and WebAuthn factors live in Supabase Auth (`auth.mfa_factors`), configured in
   `supabase/config.toml` `[auth.mfa]`. Our migrations do not create or change that schema. A TOTP secret can't be
   stored as a one-way hash, because the server has to compute codes from it. Supabase Auth keeps it encrypted at
   rest when an encryption key is configured.

## Why it matters

Gate 4 asks for pgTAP coverage of every Section 7.5 invariant. This part of invariant 8 can't be tested because
nothing implements it, and for TOTP a hash isn't technically possible.

## Suggested fix

- Decide whether Atlas issues recovery codes. If it does, add `private.mfa_recovery_codes` (bcrypt hash, used_at,
  shown once by an RPC that returns the plaintext only at generation) and a pgTAP suite naming
  `inv_08_token_rpcs_hashed_secrets`.
- Reword the second-factor clause to "second-factor secrets are held encrypted by the auth service and never
  selectable by tenants". On the local stack neither anon nor authenticated can select `auth.mfa_factors`; a pgTAP
  assertion naming the invariant code could hold that.

## Resolution (A99)

XOS issues recovery codes itself (migration 1560, ADR 0055): Supabase Auth v2.197.0 has its own behind a
setting the local CLI cannot turn on.

- `private.recovery_codes` keeps a bcrypt hash of each code, never the code, and no signed-in role can select it.
  `app.generate_recovery_codes()` returns ten codes once (step-up and a verified second factor first); a new set
  deletes the old one.
- `app.redeem_recovery_code(code)` spends one on the caller's own live session only, in one transaction, and writes
  the amr claim and aal2 Supabase Auth writes for a verified factor; a spent code never matches again, and five wrong
  codes in 15 minutes lock further tries. Use is on the person's account security trail and notifies them.
- Atlas and Gateway offer the codes at the sign-in challenge and in the step-up dialog, and make and remake them on
  Security. `supabase/tests/1560_recovery_codes.test.sql` names `inv_08_token_rpcs_hashed_secrets`.

The second-factor clause stands as the finding suggests: TOTP and WebAuthn secrets are held by Supabase Auth and are
never selectable by tenants. The owner approved the rewording on 2026-10-23 (ADR 0033, decision 56), and the spec's
invariant 8 now says so. Migration 1591 restates the registry row in `private.invariants` (migration 1220) in those
words (`supabase/tests/1591_invariant_8_wording.test.sql`).
