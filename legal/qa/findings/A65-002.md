# A65-002: Authentication stops at password, magic link and OAuth

## Finding

Section 9 requires email with password, magic link, passkeys, Google, Apple and Microsoft OAuth, Enterprise
SAML SSO and SCIM, MFA with TOTP and passkeys enforced per role, a per-org session lifetime, and step-up for billing,
data export, role changes and API key creation. Section 4.5.6 personal setting 4 is "Security: passkeys, MFA,
sessions and devices".

What exists: password and magic link (`signInWithPassword`, `signInWithOtp`), OAuth for the three providers when
configured (`apps/atlas/lib/auth/providers.ts`), and `private.session_aal()` refusing Restricted exports, the 1099
export, SCIM token issue and break-glass without aal2.

What does not:

- **MFA.** No shell enrolls or challenges a TOTP factor, so no session ever reaches aal2. Every step-up check is
  unreachable (A59-019 reports the break-glass dead end). Atlas Personal settings, Security is an empty state;
  Gateway Security offers only sign-out.
- **Passkeys.** No WebAuthn registration or sign-in; no `user_passkeys` or `webauthn_challenges` tables
  (Section 7.3 identity).
- **Sessions and devices.** No list of sessions or devices to sign out of.
- **MFA policy and session lifetime.** Stored but not enforced (A65-001).
- **Step-up coverage.** Billing, role changes and API key creation do not require aal2.
- **SAML SSO.** `saml_sso` is plan-gated and SSO just-in-time joins exist in the database (0638), but no sign-in
  path calls `signInWithSSO` and no IdP can be configured from Settings.
- **SCIM 2.0.** `packages/integrations/src/identity/scim.ts` handles SCIM requests, but no HTTP endpoint serves it
  (ADR 0024 consequences).
- **OAuth 2.1 with PKCE.** App registry and consent grants exist (0638); no authorization or token endpoint
  (ADR 0024, ADR 0026 security item 7).
- **Recovery codes.** A54-001 (open) records that no recovery codes exist.

## Why it matters

Without MFA the platform does not meet NIST SP 800-63B (Section 14.2) or ASVS Level 2 authentication controls,
Restricted data can never be exported, and break-glass cannot be used. Enterprise customers cannot sign in with
their IdP or provision users.

## Suggested fix

1. TOTP enrollment, challenge and recovery codes in Atlas and Gateway Personal settings, Security, using
   Supabase Auth MFA, with a step-up dialog any aal2 refusal can open (closes A59-019 and A54-001 with it).
2. Passkeys through Supabase Auth WebAuthn where available, or the `user_passkeys` tables of Section 7.3.
3. Sessions and devices list with sign-out.
4. Enforce `security.mfa_policy` by role and `security.session_hours`.
5. Require aal2 for billing changes, role grants and API key creation.
6. SAML SSO: an Enterprise settings panel for the IdP and a "Sign in with SSO" path.
7. An Edge Function serving the SCIM 2.0 handler, with the token flow that already exists.
8. The OAuth 2.1 authorization and token endpoints, then move per-operation scopes as ADR 0026 item 7 describes.
