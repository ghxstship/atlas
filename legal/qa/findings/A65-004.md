# A65-004: Settings sections without a surface

## Finding

`SettingsSectionPage` (`apps/atlas/components/settings/settings-page.tsx`) shows a section's registered settings
and the panels modules contribute. A section with neither renders an empty state whose action links to the same
page with `?create=1`, which nothing handles. 21 sections are in that state:

| Section                            | Backend that exists                                                                                  |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------- |
| API Keys and Service Accounts      | `api_keys`, `service_accounts`, scopes (0921, 0922, 0936) and operations                             |
| Webhooks                           | `webhook_endpoints`, signed deliveries, `webhookDeliveries.replay` (0510)                            |
| Spend Authority                    | `app.spend_authorities`, enforced in approval RPCs (0320, 0360)                                      |
| Separation of Duties               | `app.separation_of_duties_rules` registry (1150); orgs may tighten rules                             |
| Custom Fields                      | `custom_field_definitions` and values (0540)                                                         |
| Canon Extensions                   | `canon_extension_proposals` (0490); a page exists under Canon                                        |
| Data and Privacy                   | DSAR workflow, retention policies, legal holds, exports (0501, 0530)                                 |
| Templates, Usage, Partner          | Templates (1032), usage rollups (0510), partner console (1060); A59-032 and A59-020 are in progress  |
| Audit Log                          | Served by Activity, Audit log                                                                        |
| Notifications Defaults             | None: no org-level defaults or mandatory categories (A65-021)                                        |
| Departments and Disciplines in Use | None: no table records them                                                                          |
| Locations and Venues defaults      | None                                                                                                 |
| Automations                        | None (A65-010)                                                                                       |
| Personal: Security                 | See A65-002                                                                                          |
| Personal: Notifications            | `person_notification_preferences`; Gateway already renders a matrix (`notification-preferences.tsx`) |
| Personal: Calendar Feeds           | `calendar_feeds` (A65-018)                                                                           |
| Personal: Connected Apps           | `oauth_grants` (0638)                                                                                |
| Personal: Developer                | Personal API tokens: not modeled                                                                     |
| Personal: Payout and Tax           | `payout_accounts`, `tax_forms` (0730); Gateway has the form                                          |

Workspace and team settings pages (Section 4.5.6, "short pages holding only the settings their scope can
override") do not exist in the sitemap.

## Why it matters

The API and database for most of these are built and tested, but an Admin cannot reach them in Atlas: spend
limits, webhooks and API keys can be configured only through the API, and DSARs only through SQL or the API.

## Suggested fix

Contribute a panel per section through `components/settings/contributions/`, reusing the data functions that
exist (`@xos/data`). Port the Gateway notification matrix and payout form to Atlas. Model departments in use,
location defaults and personal API tokens (small tables with RLS and pgTAP). Add workspace and team settings
nodes to the sitemap (an ADR 0006 amendment). Then add the test above so no section ships empty again.

## Resolution (A86, RRR-131, 2026-10-21)

Every settings section that rendered only its empty state now shows a surface over its backend. Atlas panels are
contributed through `apps/atlas/components/settings/contributions/a86.tsx` (code in `components/settings/surfaces/`);
Gateway draws them in `apps/gateway/components/settings/surfaces.tsx`.

| Section                            | Surface                                                                                                                                                                                             |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API Keys and Service Accounts      | Service accounts (create with a role, retire), API keys (create for a service account, scoped, expiring, shown once; revoke), members' personal tokens, and the `developer.personal_tokens` setting |
| Webhooks                           | Endpoints (create with events, signing secret shown once; pause, resume, remove) and the last 20 deliveries with Send again                                                                         |
| Spend Authority                    | Limits per role or member, document type and currency, with the dual approval line; add and remove                                                                                                  |
| Separation of Duties               | The rules every org keeps, read-only (tightening per org is not modeled)                                                                                                                            |
| Custom Fields                      | Fields per built-in table with type, required and filterable; choices for Choice fields                                                                                                             |
| Canon Extensions                   | The org's approved and waiting extensions, and the way to the Canon page that proposes and decides them                                                                                             |
| Data and Privacy                   | Data requests with their clock and moves, legal holds (place, release), exports, classification and retention                                                                                       |
| Templates, Usage, Partner          | A61's panels (landed first in batch-c); Usage also shows A86's metered usage by billing month (1433 `app.org_usage`)                                                                                |
| Audit Log                          | The latest audit events and the way to the full log                                                                                                                                                 |
| Notifications Defaults             | A80's org defaults panel, which landed before A86                                                                                                                                                   |
| Departments and Disciplines in Use | New model (1430) with a save-bar form; the feed department picker and the project scope matrix narrow to it                                                                                         |
| Locations and Venues defaults      | New model (1431) with a save-bar form; a new venue starts from it                                                                                                                                   |
| Automations                        | What runs on its own today: scheduled report deliveries, recurring records, active approval policies and live webhooks. Rule-based automations remain A65-010                                       |
| Personal: Security, Calendar Feeds | A77's and A84's panels, which landed in batch-c during A86                                                                                                                                          |
| Personal: Notifications            | A80's matrix                                                                                                                                                                                        |
| Personal: Connected Apps           | The person's OAuth grants with revoke (1433 `app.my_oauth_grants`), in Atlas and Gateway                                                                                                            |
| Personal: Developer                | Personal API tokens (1432): hashed, shown once, scoped, expiring, revocable, audited, step-up to create; in Atlas and Gateway, and usable against the API through the api-token exchange            |
| Personal: Payout and Tax           | The Gateway lists ported to Atlas (last four only)                                                                                                                                                  |

Gateway's company sections that only pointed elsewhere now hold content: Service Regions and Capabilities (edit the
company profile's regions and categories), Notifications Defaults (new model 1434, applied when a team member has
not chosen) and Danger Zone (make an Account Owner, step down, leave).

The workspace and team settings pages exist (ADR 0006 amendment of 2026-10-21):
`/{org}/settings/workspaces/{workspaceSlug}` and `/{org}/settings/teams/{teamId}`.

## Follow-up (A135, RRR-197, 2026-10-28)

Separation of Duties is no longer read-only. Orgs tighten it (Section 8.2): the built-in rules are marked Always on
with no control, and holders of `org.separation_of_duties.write` turn on stricter options that the database enforces
with their own rule codes: `sod_document_creator`, `sod_receiver_po_approver` and `sod_change_order_requester_steps`
(migrations 2280 and 2281, ADR 0113, pgTAP 2280, journey `apps/atlas/e2e/a135-separation-of-duties.spec.ts`).
