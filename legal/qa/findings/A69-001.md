# A69-001: GET calls skipped every failed-attempt counter

## Finding

PostgREST runs a GET call of an RPC in a read-only transaction, and it runs volatile functions that way too. The
anonymous token RPCs count a wrong access code with a write:

- `private.resolve_advance_token` and `private.resolve_document_token` add one to `failed_attempts` and lock the link
  after 5 wrong codes;
- `verify_certification`, `calendar_feed_events` and `record_cookie_consent` note a failure against the caller's
  address in `private.rate_limit_events`.

Through GET the write failed with 25006, so the counter never moved, while a right code reached the `return query`
before any write and came back with its rows. Reproduced on the local stack: eight wrong codes through
`GET /rest/v1/rpc/preview_advance` answered 405 and left `failed_attempts` at 0, and the right code then returned the
advance packet. The different errors of a hit and a miss (UPDATE against INSERT) also told them apart for
`calendar_feed_events`.

A second, smaller flaw sat in the same resolvers: they read the token row without a lock, so a burst of parallel POSTs
all read `failed_attempts = 0` and each got a guess before the fifth failure locked the link.

## Impact

Anyone holding an advance link or an engagement document signing link (a forwarded email, a shared screen, a log line,
see A69-008) could try all 1,000,000 access codes. The access code is the second factor that protects exactly that
case, and the lockout after 5 tries was the control that made 6 digits enough. The threat model's residual risk note
("Lockout still holds for POST, which is the only path that can return data") was wrong: GET returned data.

Agreements were not affected, because `private.agreement_by_token` already read with `FOR UPDATE`, which a read-only
transaction refuses.

## Fix

- `private.require_read_write()` raises one fixed 25006 error ("this call changes data: send it with POST") in a
  read-only transaction, before anything is looked up.
- Every lockout and per-address limit helper calls it first: `private.resolve_advance_token`,
  `private.resolve_document_token`, `private.agreement_by_token` and `private.rate_limit_exceeded`. Every volatile
  `api_public` RPC goes through one of them.
- The two resolvers lock the token row (`FOR UPDATE`) before comparing the code, so parallel guesses queue and the
  fifth wrong code locks the link for all of them.

No client calls these RPCs with GET (supabase-js uses POST unless asked), so nothing in Atlas, Gateway or Compass
changes.

## Test

`1295_token_lockouts_need_writes.test.sql` calls every volatile `api_public` function, including ones added later, in
a read-only transaction and expects the fixed refusal (record_cookie_consent is listed as checking no secret). It shows
that a wrong and a right code through GET are refused alike and count nothing, that the lockout through POST still locks
on the fifth wrong code, and that both resolvers lock the row. With the guard replaced by an empty function, four of its
assertions fail.
