# A69-009: Break-glass reach was keyed on the person, not the session

## Finding

The review was asked whether break-glass expires exactly, audits fully and requires aal2.

- **aal2 only at the start.** `app.start_break_glass` checks the second factor, but the emergency branch of
  `private.person_capability_reach` and the allow-list bypass in `app.network_access` checked only that the person held
  an open session. For the hour, any session of the holder reached the Owner role's capabilities and passed the IP
  allow-list, including a password-only (aal1) session on another device, which is what a stolen password gives.
- **Delegates inherited it.** The delegation branch asks for the delegator's reach, which included the break-glass
  branch, so whoever held the holder's approvals by delegation reached every approval the Owner role holds without a
  second factor, a reason or a notice to the Admins.
- **Expiry.** In the database a session ends exactly (`expires_at = started_at + 1 hour`, compared with `now()`), but
  the API reused an allow-list answer for 30 seconds, so an admission by break-glass outlived the session by up to 30
  seconds there.
- **Audit.** The start and an early end were written to the ledger; a session that ran its hour left no event.

## Fix

- The break-glass branch applies only to the signed-in holder themself, in an aal2 session that is not an API key; it
  no longer flows through delegations or to other sessions.
- `app.network_access` lifts the allow-list only for such a session (`private.break_glass_reaches_me`).
- The API never caches an admission from outside an enforced list, so it ends when the session does.
- `private.audit_expired_break_glass` writes `break_glass_sessions.expired` once for every session that ran its hour,
  every five minutes (pg_cron).

## Test

`1298_break_glass_second_factor.test.sql` covers the aal2 session (reach and allow-list), an aal1 session and an
API-key token of the holder (neither), a delegate of the holder's approvals (none), the reach seen from outside the
holder's session, and the expiry audit written once. Against the 1203 function four of its assertions fail. The 1203
suite now steps up before its "during" checks, and `auth.test.ts` covers the cache.
