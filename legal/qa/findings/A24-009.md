# A24-009: Route JavaScript over budget on every page

## Finding

Section 18, gate 10 caps route JavaScript at 200 KB gzip. Lighthouse against production builds
measured 466 to 717 KB on every key page of Atlas, Gateway and docs (`legal/qa/performance-results.md`).

The largest script on every page is one chunk of about 1.0 MB raw, 305 KB gzip (334 KB on docs). It is
the whole message catalog: every namespace in en-US and es-US, inlined by `JSON.parse`. It reaches
the browser through:

- `packages/ui/src/lib/i18n.ts`, which imports `getMessages` from `@xos/i18n`; every client component
  that imports `@xos/ui` pulls in `catalogs.generated.ts`;
- `apps/atlas/app/global-error.tsx` and `apps/gateway/app/global-error.tsx`, client components that
  import `getMessages` directly.

Atlas signed-in pages carry a second large chunk, about 98 KB gzip (349 KB raw), that is mostly Zod
schemas (391 `zod` references), which suggests `@xos/schemas` modules imported by client components.

## Repro

`pnpm --filter @xos/testing lighthouse` against `next start` builds, or open
`apps/atlas/.next/static/chunks/` after `next build` and find the chunk that begins with
`JSON.parse('{"views":{"label":"View"`.

## Expected

The browser receives only the active locale's namespaces a page uses: `@xos/ui` takes its strings
from the provider (or imports only the `ui` namespace file), the server passes the page's namespaces
to `NextIntlClientProvider`, and `global-error.tsx` imports only the strings it shows. That removes
about 305 KB gzip from every page, which brings Atlas sign-in (481 KB) and Gateway pages (519 to
530 KB) near the budget; Atlas signed-in pages also need the Zod chunk kept on the server.

## Fix (A37, RRR-81)

- The catalog no longer reaches the browser. `@xos/ui` imports only the en-US `ui` namespace and
  takes other locales from `XOSProvider`; both global-error boundaries import their three strings
  from generated client extracts; client code checks locales through the catalog-free
  `@xos/i18n/locales`. The next-intl client provider carries only the namespaces each app's client
  components read.
- Zod and the YAML parser left every page (`@xos/ia` constants split from its schema), help article
  bodies load when the panel opens, the chart library loads only where a chart draws, and small
  hooks moved out of modules that dragged tables along.
- Route JavaScript: Atlas sign-in 481 to 183 KB, Atlas signed-in pages 632 to 717 KB down to 256 to
  331 KB, Gateway 519 to 530 KB down to 202 to 213 KB, docs 466 to 169 KB (build measurement;
  Lighthouse adds Next.js link prefetches, see `legal/qa/performance-results.md`).

## Still open (A37; since closed)

Atlas signed-in pages and Gateway pages stay over 200 KB. The causes are listed in
`legal/qa/performance-results.md`: the Next.js and React runtime (128 KB), the icon registry
(15 KB), the Atlas shell, tables and charts. Each page holds a ceilinged budget in
`packages/testing/bundle-ceilings.json`, so CI fails on growth. Getting Gateway under budget needs
the icon sprite or next-intl precompilation, proposed for an owner decision.

The icon sprite (A41) and on-demand components (A46) brought every key page except Atlas Projects
under budget; Projects (219 KB) held a ceiling of 225,464 bytes.

## Fix for Projects (A48, RRR-92)

Projects went from 224,466 to 201,135 bytes gzip (budget 204,800), and project overview from
204,656 to 196,361. The Projects ceiling is removed; `bundle-ceilings.json` holds none.

- **Cause.** The default table view loaded TanStack Table (core, store and React bindings, about
  11 KB) with TanStack Virtual (6.6 KB) in one 22 KB chunk. Tree shaking worked: unregistered
  features left only about 1.5 KB, so registering fewer features could not close the gap.
- **DataTable** (`packages/ui/src/DataTable`) computes column widths and pinned offsets itself, as
  TanStack's sizing and pinning features do; keyboard resize and reset change that state directly.
  A pointer drag runs on TanStack Table, controlled, from `DataTableResizer.tsx`, which loads when a
  pointer enters a resize handle or a handle takes focus. Rendering, ARIA and keyboard behavior are
  unchanged; unit tests cover the drag before and after the engine loads.
- **Shell and boundaries:** the page skeleton is its own client module (loading boundaries pulled
  the `components/projects/ui.tsx` barrel), `@xos/ui` Skeleton has its own module, the org error
  boundary navigates home without next/link, the client sitemap ships packed, and Turbopack merges
  chunks below 200,000 raw bytes.
