# A69-007: Security settings that protected no one

## Finding

Settings, Security offers three org settings, saved through the registry (0851):

| Setting                         | What the page says                                                          |
| ------------------------------- | --------------------------------------------------------------------------- |
| `security.mfa_policy`           | "Who must use a second factor to sign in": Optional, Admins, Everyone       |
| `security.session_hours`        | "How long a sign-in lasts before the person signs in again", 1 to 720 hours |
| `security.idle_timeout_minutes` | "Sign out after this many minutes without activity", 5 to 1,440             |

No sign-in flow, proxy, API runtime, RLS helper or job reads any of them. Atlas and Gateway also have no screen to
enroll a second factor or to verify one, so no Atlas session ever reaches aal2. The Security Overview promises MFA that
"organizations can require per role" and "configurable session lifetime".

## Impact

- An Owner who chose "Everyone" believed a stolen password was no longer enough. It was: members kept full access with a
  password alone. ADR 0032 retired settings like these because they "would report protection that does not exist".
- The features that do require aal2 in the database (break-glass, Restricted payroll and 1099 exports, SCIM token
  issuance) fail closed, because nothing in Atlas can produce an aal2 session. That is safe but means they cannot be used.

## Mitigation in this review

Building enrollment, challenge and step-up screens is a feature, not a fix. Until it exists:

- Migration 1299 keeps each setting at its default (`optional`, 336 hours, 60 minutes) and refuses any other value with
  `setting_not_enforced`. No org held another value.
- The help text says "Not available yet: XOS does not enforce it", in en-US and es-US, and the page explains the refusal.
- The Security Overview no longer claims org-required MFA or a configurable session lifetime.

## Owner decision

1. Build MFA in Atlas and Gateway: TOTP and passkey enrollment, the challenge after sign-in, and step-up for the aal2
   features. Supabase Auth already has factors enabled (`supabase/config.toml` `[auth.mfa]`).
2. Enforce `security.mfa_policy` where sessions are checked (Atlas membership resolution and the API authenticator,
   beside the IP allow-list) and in the database for the capabilities it covers, then lift the 1299 guard.
3. Choose how sessions end: Supabase Auth's project-wide time-box and inactivity timeout, or per-org enforcement in Atlas
   and the API from the session's `amr` time and a last-activity mark.

## Test

`1299_unenforced_security_settings.test.sql` refuses the non-default values, accepts the defaults and checks that no
org holds a value that would claim protection. `settings-registry.test.ts` checks the refusal and the help text in both
locales.
