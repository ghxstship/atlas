# A108-002: Stored totals on wholesale statements

## Severity rationale

Low. The statement and its lines are append-only (`private.guard_wholesale_statement_totals` allows only the one
update that fills the totals), so the stored values cannot drift from the lines after the statement is issued. But Section 3.15 rule 2 says totals and counts are derived, never stored by hand, unless the
register lists them for measured performance, and these four are not in the register.

## Location

`supabase/migrations/1060_partner_console.sql`:

- `:283` to `:286`: `app.wholesale_statements.client_count`, `list_total_minor`, `wholesale_total_minor` and
  `unpriced_count`.
- `:389` to `:394`: `app.run_wholesale_billing` inserts the lines into `app.wholesale_statement_lines`, then sets the
  four columns to `count(*)`, `sum(list_minor)`, `sum(wholesale_minor)` and `count(*) filter (where list_minor is null)`
  over those lines.

## Reproduction

```sql
select s.id, s.client_count, s.list_total_minor, s.wholesale_total_minor, s.unpriced_count,
  count(l.id), coalesce(sum(l.list_minor), 0), coalesce(sum(l.wholesale_minor), 0),
  count(l.id) filter (where l.list_minor is null)
from app.wholesale_statements s
left join app.wholesale_statement_lines l on l.wholesale_statement_id = s.id
group by s.id;
```

Each stored column equals the aggregate beside it.

## Suggested fix

Drop the four columns and serve them from a `security_invoker` view over the lines (`app.wholesale_statement_totals`),
which the partner console and the API read; the statement keeps `wholesale_discount_bps` and `currency_code`, which
are facts of the run. If a measurement shows the aggregate is too slow for the partner console, register the columns
instead, with the RPC as their refresh rule and the measurement as the reason. Either way, remove the four `finding`
entries from the register's `stored` list.
