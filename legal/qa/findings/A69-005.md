# A69-005: CSV formula injection

## Finding

Every CSV writer quoted commas, quotes and line breaks but left a leading `=`, `+`, `-` or `@` alone:

- `toCsv` in `@xos/data/finance`: the UPL export, the 1099-NEC file, the report pages' CSV button and the API's UPL
  handler;
- `previewCsv` in the report builder: CSV downloads and the scheduled report files the `report-run` worker stores and
  emails;
- the org archive's CSV (`lifecycle.ts`);
- the CLI's `formatCsv` (`xos transfer` exports).

Their cells hold text that members and external parties type: vendor and payee legal names, record titles, scope node
names. XLSX files were safe (exceljs writes strings as strings) and PDFs draw text.

## Impact

A vendor whose legal name was `=HYPERLINK("https://evil.example","Open invoice")` or a DDE payload turned into a live
link or a prompt to run a command on the finance team's machine when they opened the 1099 or UPL export in Excel.

## Fix

`csvField()` in `@xos/data/csv` gives a text value that starts with `=`, `+`, `-`, `@`, a tab or a carriage return a
leading apostrophe (the OWASP neutralization) and leaves plain numbers such as `-12.50` alone, then quotes as RFC 4180
says. All three `@xos/data` writers use it. The CLI, which does not depend on `@xos/data`, neutralizes the same way and
strips the apostrophe again on import, so an export round-trips. The archive's JSON keeps every value exactly. The SQL
payroll export holds only codes, numbers and ids, so it needed no change.

## Test

`csv.test.ts` covers each trigger, plain numbers and the finance and report writers end to end; the archive and CLI
suites cover theirs, the CLI round trip included. The Semgrep rule `xos-csv-quoting-outside-csv-field` refuses CSV
quoting written by hand outside the two helpers.
