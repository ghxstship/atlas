# A65-016: Section 8.6 is half built

## Finding

Section 8.6 sets, per classification, export rules (built: `app.request_export`, 0530), share links (allowed;
with expiry; with expiry and access code; never for Restricted) and watermarks (viewer email and timestamp on
Confidential and Restricted PDFs and images).

- Share links exist only as two values of `app.file_access_action` (0501). No table, RPC, operation or UI creates or
  opens one.
- `export_jobs.watermark` is set for Confidential and Restricted exports, but no renderer reads it; generated PDFs
  (ADR 0031) and image downloads carry no watermark.
- The column registry (`private.column_classifications`, Section 8.3) records only the 19 columns above Internal;
  nothing is ever classified Public, so the "Public: share links allowed" row has no column to apply to.

## Why it matters

Confidential documents leave without a trace of who downloaded them, and people share files by other means.

## Suggested fix

A `share_links` table with hashed tokens, expiry and access codes, refused for Restricted, opened through an
`api_public` token RPC that logs `Share Link Opened`; a watermark step in the PDF renderer and image download route
when the classification calls for it.

## Resolution, part 2: uploaded PDFs (A103, RRR-148)

- **Uploaded Confidential and Restricted PDFs carry the watermark.** The web shell stamps the viewer's email and the
  time on every page of an uploaded PDF (pdf-lib 1.17.1, `packages/data/src/documents/pdf-watermark.ts`), over the
  pages as they were, in the page's own orientation and as artifacts, for in-app downloads (`/files/{version}`) and
  share links alike (ADR 0061). A crafted page cannot hide the line: what the page leaves open is closed before it,
  and a page that would swallow it is refused. Reading is bounded (50 MiB, 5,000 pages, 256 MiB inflated).
- **Confidential PDFs may be shared by link** (migration 1690): the share link guard refuses only the images the
  watermark cannot carry (HEIC, WebP, GIF). Restricted files still never get a link.
- **Only the web shell receives a copy that must carry the mark** (migration 1691). The file-download Edge Function
  hands a Confidential or Restricted PDF or image only to a caller holding the handover secret
  (`XOS_FILE_HANDOVER_SECRET`, set in the function and in Atlas), so a link's recipient who calls
  `api_public.open_share_link` and the function directly gets nothing. In-app downloads of those files go through the
  same handover, and the attachments storage policy no longer lets a capability holder read them straight from
  Storage. The Owner with step-up still reads originals, for the full org export of Section 14.7.
- **A copy that cannot carry the mark is refused, never sent unmarked:** an image other than PNG or JPEG (by the
  database), an encrypted, unreadable or oversized PDF (by the web shell), and every such file while the handover
  secret is not set, in en-US and es-US.
- **Regression tests:** `packages/data/test/documents/pdf-watermark.test.ts` (the line on every page, the pages kept,
  rotation, unbalanced and swallowing pages, reversed boxes, XFA, the reading limits, encrypted and unreadable files),
  `apps/atlas/test/file-delivery.test.ts`, `apps/atlas/test/file-routes.test.ts` (both routes' handover and
  refusals), pgTAP `supabase/tests/1690_uploaded_pdf_watermarks.test.sql` and
  `supabase/tests/1691_file_handover.test.sql`, and the journey `apps/atlas/e2e/a103-pdf-watermarks.spec.ts`, which
  also calls the open RPC and the function directly and gets 404.
- **Owner step:** set `XOS_FILE_HANDOVER_SECRET` to the same random value in the file-download function's secrets and
  in the `atlas` Vercel project, per environment (`infra/runbooks/production.md`). Until then those files are refused.
- **Still open here:** watermarks on exports and report PDFs (parts 1 and 3, A102).
