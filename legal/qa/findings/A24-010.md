# A24-010: API latency in a populated tenant

## Finding

The k6 tenant smoke (10 virtual users, demo tenant, local stack and a production build of Atlas on
one laptop) measured reads at p50 107 ms and p95 513 ms, and record creation at p50 113 ms and p95
623 ms, against Section 5.1's 250 ms and 400 ms. The platform smoke (20 users in two small tenants)
read at p95 268 ms.

Single unloaded requests show where the time goes, for a member added by the load fixture
(load-99-1, Producer in the demo tenant) against the seeded Producer:

| Request                     | Atlas API, load member | Atlas API, seeded Producer | PostgREST direct, load member |
| --------------------------- | ---------------------- | -------------------------- | ----------------------------- |
| GET /me                     | 200 ms                 | 98 ms                      | not applicable                |
| GET /projects?limit=25      | 236 ms                 | 47 ms                      | 7 ms                          |
| GET /records?limit=50       | 347 ms                 | 146 ms                     | 7 ms                          |
| GET /notifications?limit=20 | 168 ms                 | 45 ms                      | 5 ms                          |

The database answers in single-digit milliseconds, so the extra time is in the API runtime per
request: credential verification, org resolution (`getCurrentPerson` and `listMyOrganizations` run
for every request in `runtime/auth.ts`), and the Postgres rate limiter (`app.take_api_rate_limit`, a
write per request). Why a newly added member costs more than a seeded one is not established; both
carry one membership and the same JWT claims.

Local numbers are indicative only: staging runs the API at the edge with pooled connections. The
full-scale runs in `packages/testing/README.md` decide the objective.

## Expected

p95 under 250 ms for reads and 400 ms for writes at 500 users in one tenant on staging. Profile the
per-request auth path: cache the org binding and person for the token's lifetime, and batch the
rate-limit write.

## Fix (A37, RRR-81)

`Server-Timing` on each response showed the runtime spent 36 to 41 ms of every request resolving the
caller: a Supabase Auth round trip (`getUser`) and the person and membership reads.

- Session tokens (ES256 or RS256) are verified against the project's JWKS, cached in the process
  for 10 minutes with one refetch for an unknown key id and a 30 second backoff when the endpoint is
  down. HS256 tokens, unknown keys and other issuers still go to Auth.
- The caller's person and memberships are reused for 30 seconds; a missing person is never cached,
  and RLS still checks membership on every query.
- `records.list` composes `record_key` from one projects read: the `record_display_key` computed
  column re-evaluated the projects read policy per row (40 ms for 22 rows).
- The rate limiter stays a Postgres write per request (2 to 3 ms); batching would trade exactness
  across instances for little.

Unloaded: /me 200 to 7 ms, /projects 236 to 9 ms, /records 347 to 16 ms, /notifications 168 to
6 ms. k6 tenant smoke: reads p50 9.0 ms, p95 18.4 ms; record creation p50 32.6 ms, p95 44.4 ms.
Platform smoke: reads p95 17.2 ms. Both pass every threshold. The full-scale staging runs remain
A26's.

The same per-row policy cost applies wherever Atlas pages select `record_display_key` for many rows;
the database owner may want a cheaper form of that column.
