# A108-003: Parent values copied onto child rows

## Severity rationale

Low. No copy here leaks data, and eight of them are kept equal to the parent by a guard or are fixed on both sides.
The others can drift: nothing stops a write that disagrees with the parent, so a reader that trusts the copy gets a
different answer from one that joins. Section 3.15 rule 1 says no column restates a fact stored elsewhere, and a
stored copy needs a register entry with its refresh rule and measured reason. These have none.

Each column here holds the same value as a column of a parent that its foreign key requires (the key is `not null`),
so the copy is never the row's own value. Copies through an optional link, where the row needs the value without the
parent, are the row's own and are listed in the register as `own`; they are not part of this finding.

## Reproduction

`supabase test db` with any of these entries removed from `restated` in `docs/adr/denormalization-register.yaml` (and
the generator rerun) fails `1282_normalization_lints` test 3, naming the column and its parent. For one pair:

```sql
select count(*) from app.shift_claims c join app.shifts s on s.id = c.shift_id where c.project_id <> s.project_id;
```

Nothing in the schema keeps this at zero.

## Suggested fix

For each column, one of:

1. **Drop it and join.** Most are read for row-level security or a unique index. A policy can join the parent
   (`shift_id in (select id from app.shifts where project_id in (...))`), and a unique rule on the parent's value can
   move to the parent or into a guard.
2. **Keep it equal in the schema.** Add a unique key on the parent (`unique (id, project_id)`) and make the child's key
   composite (`foreign key (shift_id, project_id) references app.shifts (id, project_id)`). The restated-column lint
   accepts a column that a composite foreign key keeps equal, and the entry leaves the register.
3. **Register it.** When the copy is kept for measured performance, add a derived entry with the guard or trigger as
   its refresh rule and the measurement as its reason, and change the entry's kind to `registered`.

The `auth` copies (`private.auth_factor_labels.user_id`, `private.session_devices`) exist because `auth` tables are
Supabase's; option 3 with the reason "RLS reads the person's own rows without joining `auth`" is the likely outcome.
