# A65-017: Security checks written but not run

## Finding

Section 9 supply chain asks for a CycloneDX SBOM per release; `legal/open-source-licenses.md` says each release
ships one and the page is generated from it. No step generates an SBOM. Section 9 testing asks for a ZAP baseline
against staging; nothing runs ZAP. Section 10.3 asks for the license compliance check in CI; `licenses:check`
exists but `.github/workflows/ci.yml` does not run it. Gate 11 records the Semgrep, audit and advisors scripts as
written but not in `ci.yml`.

## Why it matters

The Open Source Licenses page promises an artifact that is never produced, and known security checks do not
block a merge.

## Suggested fix

Add an SBOM step (`@cyclonedx/cyclonedx-npm` or `syft`) to the release workflow attached to each release; a ZAP
baseline job against staging once it exists; `licenses:check`, Semgrep, audit and advisors jobs in `ci.yml`.

## Fix (A94, RRR-139)

- **SBOM.** `infra/security/sbom.sh` scans a `pnpm install --prod` checkout with syft (`anchore/syft:v1.54.1`,
  pinned by digest) and writes CycloneDX JSON. `src/sbom.ts` checks it (CycloneDX 1.4 or later, at least 500
  versioned npm components) and renders the third-party notices list from it, grouped by license. The CI
  `supply-chain` job keeps both as the `sbom` artifact; `release.yml` attaches both to each version tag's GitHub
  release, creating a draft when none exists, and again when a release is published.
- **ZAP baseline.** `nightly.yml` `zap-baseline` scans atlas-staging and gateway-staging with
  `ghcr.io/zaproxy/zaproxy:2.17.0`. It sends `VERCEL_AUTOMATION_BYPASS_SECRET` as the Vercel bypass header, to the
  target host only, and passes with a notice while the secret is absent. `zap/baseline-rules.tsv` records the
  accepted alerts with reasons and the rules that must never alert; any High alert that is not ignored fails.
- **License check.** `pnpm --filter @xos/config licenses:check` runs in `supply-chain`. The two licenses awaiting
  counsel (sentry FSL-1.1-Apache-2.0, sharp's libvips LGPL-3.0-or-later) are recorded per package in
  `license-exceptions.json` and reported as warnings; anything else outside the allowlist fails. `buffers` 0.1.1 had
  come back into the lockfile, because a `pnpm` field in the root package.json made pnpm ignore the workspace
  overrides; every override now lives in `pnpm-workspace.yaml`, and `buffers` is gone again.
- **Semgrep** already ran in `ci.yml` (job `semgrep`, A54) and is unchanged.
- **Dependency audit.** `infra/security/src/cli.ts audit` fails on any production advisory and on a critical one
  anywhere in the tree. The three advisories without a usable fix moved from `pnpm.auditConfig` to
  `audit-allowlist.json`, with reasons and review dates.
- **Supabase advisors.** The `database` job runs them against the local stack; `supabase-advisors-staging` runs them
  against the hosted staging branch through the Management API on pushes to main, with `SUPABASE_ACCESS_TOKEN`, and
  passes with a notice while the secret is absent.
- **Pinned actions.** Every `uses:` is pinned to a full SHA with a version comment, and each pin is checked against
  the commit of its upstream tag on every push. `actions/setup-node` and `actions/setup-java` moved to v7.0.0 and
  v6.0.1, the newest releases at least two weeks old; Renovate waits 14 days before proposing an action release.
