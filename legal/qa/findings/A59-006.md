# A59-006: Inbox items read "Update / announcement.posted"

## Finding

Notifications whose kind the Inbox page does not know render as the title "Update" with the raw
kind as the detail line: `announcement.posted`, `survey.opened`, `weather.alert`. The fallback is
`apps/atlas/app/[org]/inbox/page.tsx` line 69,
`return { summary: t("inbox.generic"), detail: item.kind };`. The person cannot tell which
announcement, survey or alert it is, and there is no link to open it. Section 11.10 item 5 asks
that every item can be acted on or opened where it arrives.

The phone Inbox also shows the keyboard legend ("J K move, A approve ...") although there is no
keyboard, and the second "Needs you" approval (purchase order 44) offers only Done and Snooze,
while the first offers Approve and Reject.

## Steps

1. Sign in as owner@example.com (or viewer@example.com) on the demo seed.
2. Open /demo-productions/inbox.
3. The four For your information items read "Update" with a dotted key underneath.

## Suggested fix

Map each notification kind the platform emits to a summary and a target (announcement title and
link, survey name, weather alert with project), and fail a test when a seeded kind falls back to
the generic line. Hide the keyboard legend below `md`.

## Resolution (A61, RRR-106)

Every Inbox item reads as its notification email copy (title and summary) with the stored arguments and the actor resolved through app.person_names, links to where it opens (Open, or Enter), and never falls back to "Update" with the event key. A unit test describes every labelled kind in en-US and es-US and fails on a bare label, "undefined" or a brace. The keyboard legend is hidden below md. Journey 57: the list holds its selection by item id and moves focus to the neighbour before an acted item leaves the DOM, and Approve and Done call the public API's notification action directly, one request per key press, so twenty presses are decided in parallel instead of queueing as server actions (journey 57 passed five runs in a row).
