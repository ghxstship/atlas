# A69-010: Allow-list checks followed the bound org, RLS followed every org

## Finding

The API authenticator binds a request to one org (the token's `org_id` claim, the last-opened org cookie, or the only
membership) and asks `app.network_access` about that org alone. Row level security, though, serves the rows of every org
the caller belongs to, and the table handlers do not narrow lists or reads to the bound org.

- A request bound to no org (a person in two or more orgs, with no claim and no cookie, using a bearer token) skipped the
  allow-list check entirely and read every member org's rows.
- A request bound to an org without a list still reads, by id or in a list, the rows of another member org whose list
  refuses the caller's address.

## Impact

A person who belongs to an org that enforces an allow-list and to another org could read the first org's data through
the API from outside its networks. They could do the same by calling the Supabase endpoint directly, which ADR 0034
decision 5 records, so this was not a new capability, but the API did not hold the line it documents.

## Fix

A request bound to no org now passes the allow-list of every org the caller belongs to, or is refused with 401.

## Owner decision

The remaining case has the same root cause as decision 5: RLS cannot see the caller's address. Two ways close it:

1. Route all data access through the API and narrow every tenant list and read to the bound org (ADR 0007 item 1
   already says the org comes from the credential), so an org's rows are served only to requests its list admitted.
2. Refuse a session in the API whenever any of the caller's orgs refuses the address. Simpler, but it blocks a
   consultant's work in an unrestricted org while away from another org's network.

## Test

`auth.test.ts`: a request bound to no org is refused from an address one member org's list refuses, and admitted from
an address every list admits.
