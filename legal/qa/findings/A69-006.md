# A69-006: Confused deputy in the integration worker

## Finding

`app.enqueue_integration_sync(..., p_source_uri)` stored the `<bucket>/<path>` of the file a run imports after a length
check only. The integration worker (`packages/integrations/src/worker.ts`) reads it with the service role
(`supabaseTicketingSource.readFile`), which ignores storage policies. Any holder of `org.integrations.manage` could call
the RPC through PostgREST with `onboarding-uploads/<another org>/<file>`, `attachments/...` or `report-results/...`.

## Impact

Once the worker runs, the named file would be read and parsed as an attendance CSV, with row errors (which quote the
row) written to the manager's own sync run: a cross-tenant read of other orgs' private files. It would also bypass the
upload quarantine, since the worker never checked the scan. The worker is built but not deployed, so nothing was
exposed.

## Fix

- Migration 1297: a run's source must be an imports bucket upload named the way that bucket names them
  (`imports/<person id>/<upload id>.csv|.xlsx`). A person may name only their own upload, as for import jobs (1061); the
  platform may name an upload of a member of the run's org.
- The ticketing source reads only that bucket and only a Clean file (`app.object_scan_status`); a file still scanning
  is retried, and one that failed its scan is refused.

## Test

`1297_integration_sync_source_owned.test.sql` refuses other buckets, other orgs' and colleagues' uploads, invented
names and a path that climbs out of the folder, and accepts the enqueuer's own upload; `ticketing.test.ts` covers the
worker's checks. `0636_ticketing_connectors.test.sql` now names an upload of its enqueuer.
