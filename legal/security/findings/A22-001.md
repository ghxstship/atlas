# A22-001: API key scopes are not enforced in the database

## Severity rationale

High. The attacker needs a valid API key, which is a low-privilege credential by design: the key's
scopes are its whole grant. The attack is network-reachable and needs no user interaction. With the
token it gets, the attacker gains everything the service account's role allows, including reading
and changing data outside the key's scopes, and minting invitations into the org. Scope is
unchanged (one tenant), so the rating is High rather than Critical.

## Location

- `supabase/functions/api-token/mint.ts:98` (`handleTokenRequest`) returns `access_token` to any
  caller who presents a key. The function runs with `verify_jwt = false`.
- `supabase/functions/api-token/mint.ts` (`tokenClaims`) signs the token with the project JWT secret,
  `role: authenticated`, `sub` set to the service account's user, and the scopes only as a custom claim.
- `packages/api/src/runtime/mount.ts:267` (`assertScope`) and `packages/api/src/runtime/auth.ts:235`
  (`apiKeyTokenScopes`, the 89851ef fix) enforce scopes only inside the Hono runtime.
- `private.has_capability`, `private.orgs_with_capability`, `private.project_ids_with` and the RLS
  policies built on them never read the `scopes` or `amr` claims.

## Reproduction

HTTP, against a deployed project:

```http
POST /functions/v1/api-token
Authorization: Bearer xos_live_<48 hex, a key scoped to ["crew"] on an Admin service account>
apikey: <anon key>

200 {"access_token":"eyJ...","scopes":["crew"],...}

PATCH /rest/v1/organizations?id=eq.<org id>
Authorization: Bearer eyJ...            <- the minted token, sent straight to PostgREST
apikey: <anon key>
Accept-Profile: app
Content-Profile: app
{"name":"Renamed By Crew Key"}

204   <- succeeds although "org" is not in the key's scopes
```

SQL, the same claims PostgREST sets (run `supabase/tests/security/run-attacks.sh A22-001`):

```sql
select set_config('request.jwt.claims', json_build_object(
  'sub', '<service account user id>', 'role', 'authenticated', 'aud', 'authenticated',
  'org_id', '<org id>', 'scopes', array['crew'],
  'amr', json_build_array(json_build_object('method', 'xos_api_key', 'timestamp', 0)))::text, true);
set local role authenticated;
update app.organizations set name = 'Renamed By Crew Key' where id = '<org id>';  -- 1 row
select app.create_invite_link('<org id>', '<member role id>', interval '1 day', 5); -- succeeds
select count(*) from app.api_keys where org_id = '<org id>';                      -- every key listed
```

The attack test fails 3 of 4 assertions on main. The control assertion (an `org` scoped token may
edit the org) passes.

## Impact

Any holder of a narrowly scoped key, such as an accounting sync with `finance` only, can act with the
full role of the key's service account across every module: read Confidential data the scope was
meant to exclude, change org settings, create invite links and manage other API keys. Least privilege
for integrations (Section 8.5, ADR 0003) does not hold anywhere outside `/api/v1`, including Realtime
and Storage, which accept the same JWT.

## Suggested fix

Either is sufficient. The first is preferred, because it keeps the database as the boundary.

1. Enforce scopes in the database. Add `private.credential_scopes()`, which reads `scopes` from
   `request.jwt.claims` when `amr` contains method `xos_api_key` and returns NULL otherwise. Make
   `private.has_capability` and every capability helper return false for a capability whose group is
   not in a non-NULL scope list. Keep the Hono `assertScope` check as a second layer.
2. Never hand the minted JWT to an external caller. Sign it with a key PostgREST does not trust and
   exchange it only inside the API runtime, or perform the exchange in the runtime with the service
   role and return only the `/api/v1` result.

Then rename the attack file to a numbered regression test in the default suite.
