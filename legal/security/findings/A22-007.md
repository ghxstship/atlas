# A22-007: Stored running totals on occupancy counters

## Severity rationale

Low. This is a Third Normal Form violation, not a security flaw, but gate 29 blocks release on any
violation missing from the denormalization register. Two stored values restate the sum of the
`app.occupancy_counts` ledger. When a ledger row is moved to Trash or a count is replayed out of
order, the stored values can drift from the ledger with nothing to correct them. Occupancy drives
crowd safety alerts, so a wrong number has real consequences.

## Location

- `supabase/migrations/0806_workforce_site_operations.sql:86`: `app.occupancy_counters.current_count`,
  "People inside now, kept by the door counts".
- `supabase/migrations/0806_workforce_site_operations.sql:123`: `app.occupancy_counts.count_after`,
  "Count after this entry", a stored running balance on every ledger row.
- Neither column appears in `docs/adr/denormalization-register.md`, and neither is a generated column.

## Reproduction

```sql
-- Neither column is generated.
select attrelid::regclass, attname, attgenerated = '' as stored_by_hand
from pg_attribute
where (attrelid, attname) in (('app.occupancy_counters'::regclass, 'current_count'),
                              ('app.occupancy_counts'::regclass, 'count_after'));

-- current_count is exactly the sum of the ledger, so it is derived.
select c.id, c.current_count, coalesce(sum(k.delta), 0) as ledger_sum
from app.occupancy_counters c
left join app.occupancy_counts k on k.occupancy_counter_id = c.id and k.deleted_at is null
group by c.id, c.current_count;
```

```sh
grep -c occupancy docs/adr/denormalization-register.md   # 0
```

## Impact

Section 3.15 rule 2 says derived values are never stored by hand; totals and counts are views. The
two columns are a second home for one fact. A discrepancy between the alert threshold check and the
ledger cannot be explained from the data.

## Suggested fix

Drop both columns. Expose `current_count` through a security_invoker view, for example
`app.occupancy_counter_levels`, as `sum(delta)` over live ledger rows, and compute `count_after` with a
window function in a ledger view. If a measured benchmark shows the sum is too slow for the door
counter screen, keep `current_count`, refresh it only from the ledger trigger, and add a row to the
denormalization register with the measurement.
