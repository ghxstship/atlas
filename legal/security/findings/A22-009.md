# A22-009: Scope arrays on API keys and OAuth grants

## Severity rationale

Low. ADR 0002 says there are no arrays of identifiers and relationships use junction tables. These
arrays hold capability group codes, which are keys of the capability registry, so each one is a
many-to-many relationship stored as an array. A guard trigger validates the values, but no foreign
key protects them. If a capability group is renamed or retired, keys keep a scope string that no
longer means anything, and nobody is told. A22-001 shows why scopes matter: they are the whole grant
of a key.

## Location

- `supabase/migrations/0921_api_keys.sql:15`: `app.api_keys.scopes text[] not null`.
- `supabase/migrations/0638_identity_and_verification.sql:68`: `app.oauth_grants.scopes text[] not null`.
- `supabase/migrations/0638_identity_and_verification.sql:336`: `app.scim_identities.groups text[]`.
  Group display names are matched against `app.scim_group_mappings` to assign roles, so relational
  data sits in an array here too. Its comment calls it a provider payload, but ADR 0002's payload
  exception covers JSON payload columns, not arrays that drive role assignment.
- None of the three is listed as an exception in ADR 0002 or the denormalization register.

## Reproduction

```sql
select a.attrelid::regclass, a.attname, format_type(a.atttypid, a.atttypmod)
from pg_attribute a join pg_class c on c.oid = a.attrelid
where c.relnamespace = 'app'::regnamespace and c.relkind = 'r' and a.attnum > 0 and not a.attisdropped
  and a.atttypid in (select oid from pg_type where typcategory = 'A')
  and a.attname in ('scopes', 'groups');
-- app.api_keys.scopes text[], app.oauth_grants.scopes text[], app.scim_identities.groups text[]
```

## Impact

Scope membership cannot be indexed, constrained or audited row by row. Revoking one scope means
rewriting the whole array, and the audit diff shows an array change, not a revoked grant.

## Suggested fix

Add a `capability_groups` reference table, or a view over `app.capabilities` with a stable key.
Replace the arrays with `api_key_scopes (api_key_id, capability_group)`,
`oauth_grant_scopes (oauth_grant_id, capability_group)` and `scim_identity_groups (scim_identity_id,
group_display_name)`, each with a foreign key and RLS matching its parent. The api-token exchange
then aggregates the junction rows into the JWT claim.
